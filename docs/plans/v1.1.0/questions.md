## 5. 未確定事項

推測では埋めず、回答をもらってから該当する段階に入る。「案」は判断材料としての提案で、仕様書には案のとおりに書いてある。採用は回答後。
番号は v1.0.0 の計画(Q1〜Q31)から続ける。

**2026-10-15: Q32〜Q39 はすべて確定。** Q35 は Web で確認して仕様に反映した(下記)。それ以外は案どおり。

- **Q32(署名の判定の条件)** `Signature=` の前後の文脈(`AWS4-HMAC-SHA256` が同じ行にあること)を条件にするか。
  - 案: 条件にしない。語(`X-Amz-Signature` / `Signature`)と、64 桁ちょうどの小文字の 16 進数だけで判定する。64 桁の 16 進数は SHA-256 の値の長さで、`Signature=` が付いていれば、ほぼ署名と見てよいため。SigV2(base64)は対象外
- **Q33(ドメインのない `ip-a-b-c-d`)** `ip-10-0-1-23` のような、ドメインのない形を検出するか。
  - 案: 検出する。シェルのプロンプト(`[ec2-user@ip-10-0-1-23 ~]$`)や、EKS のノード名に多く現れる。「`ip-` + 0〜255 の数字 4 つ」で、前後の文字の条件もあるので、誤検出は少ないと見込む。一方 `ec2-a-b-c-d` は、ドメインがある場合だけ検出する
- **Q34(ホスト名の IP の値の扱い)** `54-250-1-2` と `54.250.1.2` を同じ値(同じラベル)にするか。
  - 案: 別の値にする(仕様 4.3 に記載)。同じラベルにすると、`restore` で、ラベルをどちらの形に戻すか決められず、往復で 1 バイトも変わらないことを保証できない。AI が同じアドレスだと気づけない点は、README の限界に書く
- **Q35(パーティションとドメインの一覧)** 仕様 4.4 の一覧(パーティション 8 つ、ドメイン 2 つ)は、記憶に基づく。実装前に AWS のドキュメントで確認する。ISO リージョン(`aws-iso` など)のドメイン(`c2s.ic.gov` など)は、ホストの形(ECR、SQS、S3)の対象外とし、ARN だけを対象にする
  - 案: 確認した結果、一覧に差があれば、仕様を直してから実装する(この確認は、AWS のドキュメントを Web で調べてよいか、の確認も兼ねる)
  - **確認の結果(2026-10-15)**: AWS SDK の `partitions.json`、IAM の ARN のドキュメント、S3 のバケット名の規則・エンドポイントの一覧、EC2 のホスト名のドキュメントで確認した
    - パーティション 8 つは一覧どおり
    - ドメインに `amazonaws.eu`(`aws-eusc`)が抜けていたので加えた
    - ARN のサービス・リージョンの欄に、IAM ポリシーのワイルドカード `*` が入りうるので許した
    - バケット名の規則に「`.` が 2 つ続かない」「IP アドレスの形でない」を加えた
    - S3 のエンドポイント(`s3`、`s3.<リージョン>`、`s3-<リージョン>`、`dualstack`、`s3-fips`、`s3-website-` / `s3-website.`)と、EC2 のホスト名の形(`ip-…ec2.internal`、`ip-….<リージョン>.compute.internal`、`ec2-….compute.amazonaws.com`)は一覧どおり
- **Q36(バケット名の文字の規則)** 旧形式のバケット名(英大文字・`_`、us-east-1 の 2018 年 3 月より前のもの)を検出するか。
  - 案: 検出しない(仕様 4.4 の限界に記載)。今の命名規則に絞ると、`s3://` の後ろなどの判定が厳密になり、誤検出が減る
- **Q37(`s3a://`、`s3n://`)** Hadoop・Spark の形も対象にするか。
  - 案: 対象にする(仕様 4.4 に記載)。データ処理のログに多く、形も決まっているため
- **Q38(他のアカウント ID の場所)** ARN・ECR・SQS 以外の決まった形(S3 のアクセスポイントのホスト `<名前>-<アカウント ID>.s3-accesspoint.…` など)を v1.1 に入れるか。
  - 案: 入れない。v1.2 の `aws_host` のホストの表を作るときに、あわせて検討する
  - v1.2 で検討する候補(Q35 の確認で見つかったもの): S3 Control のホスト `<アカウント ID>.s3-control.<リージョン>.amazonaws.com`、アカウントのリージョン別の名前空間のバケット名(`<名前>-<アカウント ID>-<リージョン>-an`)の中のアカウント ID、EC2 のパブリックホスト名の IPv6 形式(`….ip.aws`。IP アドレスの base36 符号化)
- **Q39(合成ログ)** 性能測定用の合成ログに、AWS の値を含む行を加えるか。加えると、v1.0.0 の測定結果と単純に比べられなくなる。
  - 案: 既定の合成ログは変えない。AWS の値を含む行を加えた別の設定を用意し、`--types default,aws` の測定に使う

**2026-10-16: 段階 3 の実装前に、Q40〜Q42 を追加。同日、すべて案どおりに確定し、仕様 4.3・4.4 に反映した(Q41 の「あわせて」も、ECR・S3 のバーチャルホスト形式を同じ条件にする)。**

- **Q40(ホスト名の中のリージョンの形)** 仕様 4.3 の `.<リージョン>.compute.<ドメイン>`、`.<リージョン>.compute.internal` の「リージョン」に使える文字が決まっていない。ARN のリージョンの欄(4.4)は「英小文字・数字・`-` の 0 文字以上」と決まっているが、ホスト名の中では空にできない。段階 4・5 の ECR(`.dkr.ecr.<リージョン>.`)、SQS(`sqs.<リージョン>.`)、S3 のエンドポイント(`s3.<リージョン>.` など)でも同じ問題がある。
  - 案: ホスト名の中のリージョンは「英小文字・数字・`-` の 1 文字以上」とする(ARN の欄と同じ文字で、空は不可)。`ap-northeast-1` のような実際の形(`<2 文字>-<方角>-<数字>`)に絞ることはしない。新しいリージョン(`eusc-de-east-1` など)や、形の変わったリージョンも拾えるようにするため。誤検出は、前後の決まった部分(`.compute.amazonaws.com` など)で十分に抑えられると見込む
- **Q41(ホスト名の末尾の後ろの文字)** `ec2-` のホスト名の末尾のドメイン(`amazonaws.com` など)と、`ip-` の `.ec2.internal`・`.compute.internal` の後ろに、どんな文字が来てよいかが決まっていない。条件がないと、`ec2-54-250-1-2.ap-northeast-1.compute.amazonaws.com.example.net` や `ip-10-0-1-23.ec2.internalx` も対象になる。
  - 案: 末尾の後ろが、英数字・`-`・`_` でなく、「`.` + 英数字」でもないこと(行末は可)とする。文末の `.` と、FQDN の末尾の `.`(`….compute.internal.`)は許す。IPv4 の後ろの条件(仕様 4.3)と同じ考え方。ドメインは長いほうから照合する(`amazonaws.com.cn` を `amazonaws.com` + `.cn` と読まない)
  - あわせて、段階 4・5 の ECR・SQS・S3 のホスト名の末尾も、同じ条件にするか(ECR・S3 のバーチャルホスト形式は、ドメインの後ろが `/`・`:` などになる。SQS とパス形式は、仕様で `/` が続くことが決まっている)
- **Q42(ホスト名の大文字・小文字)** `ec2-`・`ip-`・ドメイン(`.EC2.INTERNAL` など)の大文字・小文字を区別するかが決まっていない。DNS の名前は大文字・小文字を区別しないが、AWS が付ける名前と、ログに出る形は小文字。
  - 案: 区別する(仕様に書かれた小文字の形だけを対象にする)。精度重視の方針(決定事項 16)に合わせる。段階 4・5 のホスト名・ARN も同じとする(AWS の SigV4 の語は、仕様で「区別しない」と明記されているので別)

**2026-10-17: 段階 5 の実装前に、Q43〜Q46 を追加。同日、すべて案どおりに確定し、仕様 4.4 に反映した。**

- **Q43(バーチャルホスト形式で、バケット名とエンドポイントの区切りが 2 通り以上ある場合)** バケット名は `.` を含んでよく、リージョンは英小文字・数字・`-` の 1 文字以上(Q40)なので、ホスト名の区切り方が 1 つに決まらないことがある。例: `logs.s3.backup.s3.amazonaws.com` は、「バケット名 `logs` + エンドポイント `s3.backup`(`s3.<リージョン>`)」とも、「バケット名 `logs.s3.backup` + エンドポイント `s3`」とも読める。
  - 案: エンドポイントを、ホスト名の中のできるだけ後ろ(ドメインの直前に近いほう)で取る。つまり、バケット名を最も長く取る。実際の S3 では、リージョンは決まった名前なので後者が正しい。バケット名が規則に合わない場合は、短い区切り方に戻らず、置換しない(区切り方を選び直すと、結果が分かりにくくなるため)
- **Q44(バケット名の後ろの文字)** 仕様は「バケット名の後ろが、バケット名に使える文字(英小文字・数字・`.`・`-`)でないこと」だが、これだけでは次の 2 点が決まらない。
  1. 旧形式のバケット名(英大文字・`_` を含む。仕様 4.4 の限界で「検出しない」)の一部が置換される。例: `s3://abc_def/` は、`abc` の後ろが `_`(バケット名に使える文字でない)なので、`abc` だけが置換されてしまう。受け入れ基準「英大文字・`_` を含む…は置換されない」に反する
  2. 文末の `.`(`see s3://my-bucket.`)。`.` はバケット名に使える文字なので、`my-bucket.` 全体がバケット名の候補になり、末尾が `.` のため規則に合わず、置換されない
  - 案: (1) バケット名の後ろは、英数字(大文字を含む)・`_`・`.`・`-` のどれでもないこと、とする(旧形式のバケット名は、どこも置換しない)。(2) 候補の末尾が `.` 1 つで、その後ろが上の条件を満たす場合は、末尾の `.` を文末の句点とみなして外す(バケット名は `.` で終われないので、外しても本物のバケット名を切ることはない)。バーチャルホスト形式は、バケット名の後ろが常に `.s3…` なので、この条件は `s3://` 形式・パス形式・ARN に当てはまる
- **Q45(「IP アドレスの形」の範囲)** バケット名の規則の「IP アドレスの形(`192.168.5.4`)でない」が、どの範囲の文字列を指すかが決まっていない(値が 0〜255 の正しいアドレスだけか、`999.1.1.1` のような数字の 4 つ組も含むか)。
  - 案: 「数字 1 文字以上の組 4 つを `.` で区切った形」(値の範囲は問わない)とする。S3 は IP アドレスに見える名前を作らせない規則なので、数字の 4 つ組をすべて除いておけば、本物のバケット名を見逃すことはない。正しい IPv4 アドレスの場合は、`ipv4` が有効なら、`ipv4` として置換される(同じ範囲なら `ipv4` が優先。仕様 4 章)
- **Q46(ARN の形の `arn:` の前の文字)** `aws_s3_bucket` の ARN の形には、`aws_account` の ARN にある「`arn:` の前が英数字でないこと」が書かれていない。
  - 案: `aws_account` と同じ条件(`arn:` の前が英数字でないこと)とする。同じ ARN が、種別によって検出されたりされなかったりしないようにするため
