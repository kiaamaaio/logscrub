- **Q65(キー名ベースの値が、ユーザー情報つきの URL の場合。冪等性の違反とパスワードの一部の残り)** 段階 10 のあとのコードレビュー(2026-10-18)で見つかった。Q63 の修正は `<キー名>://`(区切りの `:` の直後が `//`)だけが対象で、`=` の区切りや、区切りの後ろの空白のあとに URL が続く形では、同じ仕組みの問題が残る。段階 5 の URL のパスワードで入った、既存の問題
  - 例 1: `password=https://u:&x@db.example.com/`。キー名ベースの値は `https://u:`(`&` の手前まで)、URL のパスワードは `&x`。2 つは重ならず隣り合うので両方が置換され、`password=<secret_1><secret_2>@db.example.com/` になる。2 回目は、値の区切りだった `&` が消えているので、キー名ベースの値が `<secret_1><secret_2>@db.example.com/` 全体になり、再び置換される(`password=<secret_1>`)。Q63 と同じ仕組み
  - 例 2: `password=https://u:p&q@db.example.com/`。キー名ベースの値 `https://u:p` と URL のパスワード `p&q` が重なり、範囲が長いキー名ベースが採られる。そのため、**パスワードの残り `&q` が 1 回目の出力に残る**(`password=<secret_1>&q@db.example.com/`)。その `@` は、URL のユーザー情報の `@` としてメールアドレスから外されたまま(`urlPasswordStart` が真)なので、ホスト名も残る。2 回目は URL の形でなくなるので、`q@db.example.com` がメールアドレスとして置換される(`password=<secret_1>&<email_1>/`。冪等性の違反)
  - 起きる条件: キー名(`password`・`secret`・`token` など)の値が、ユーザー情報つきの URL で、パスワードに値の区切り(`&` `,` `;` `)` `]` `}`)を含むか、値の区切りで始まる
  - 案 A(推奨): キー名ベースの値の中に、URL のパスワードの形(仕様 4.1。`<スキーム>://<ユーザー>:<パスワード>@<ホスト名>`)があれば、キー名ベースの値として扱わない(パスワードは URL のパスワードとして置換される)。Q63 の考え方(`<キー名>://` は URL のスキーム)を、`=` の区切りと、区切りの後ろの空白のあとの URL にも広げる
  - 案 B: キー名ベースの値を、URL のパスワードの形の終わり(`@` の手前)まで延ばす。パスワードは残らないが、ユーザーやスキームも 1 つの値として置換される
  - 案 C: v1.2.0 では直さず、README の限界に書く
  - **回答(2026-10-18)**: 案 A。対象は、値の先頭(引用符で始まる場合は、開き引用符の直後)から URL のパスワードの形が始まる場合だけ(値の途中の URL は対象外)。引用符で囲まれた値も対象。冪等性のため、判定ではユーザー・パスワード・`@` の直後が置換済みの形のものも、この形に含める。仕様 4.1(値の範囲)・9 章・決定事項 20・11 章、README(キー名ベースの説明、v1.2.0 の変更点)に反映した

- **Q67(IPv6 の端のグループの切り離しと、hash の出力。冪等性の違反)** Q66 の修正のあとのファズテスト(`FuzzHashStable`)が見つけた。v1.1.0 でも起きる、既存の問題(v1.1.0 と、Q66 の実装前で、同じ入力で失敗することを確認した)
  - 例: `::1::0@0.AA` を `--mode hash` で流す。1 回目は、16 進数・`:`・`.` の連なり `::1::0` の後ろが `@` なので、端のグループは切り離さず、`::1::0` は IPv6 として解析できないので検出しない。`0@0.AA` はメールアドレスとして置換され、`::1::email_d33dcb6233c3` になる。2 回目は、hash の出力が 16 進数の英字(`e`)で始まるので、連なりが `::1::e` に伸び、後ろが英字(`m`)なので端のグループ `e` を切り離す(仕様 4.3)。実装は、最後の `:` の手前で切るので `::1:` が残り、その末尾の `:` を「単独の `:`」として外して `::1` になり、`::1` が置換される
  - 起きる条件: `::` を 2 つ含むなど、IPv6 として解析できない連なりの直後に、区切りなしでメールアドレス(または aws の値)が続き、hash の出力が 16 進数の英字で始まる(`email_`、`aws_…`)。mask の出力(`<email_1>`)は `<` で始まるので起きない

  - 案 A(推奨): 切り離しのあとの「単独の `:`」は、元の行で判断する(元の行で `::` の一部なら外さない)。`::1:` が残り、解析できないので検出しない。1 回目の動作が変わるのは、`::1::x` のような、IPv6 として解析できない連なりの後ろに英字が続く形だけ(v1.1 では `<ipv6_private_1>::x`、案 A では置換しない)。`2001:db8::x` のような形は、今も案 A でも検出しない(変わらない)

- **Q68(Q65 の判定で、置換済みの形を読む範囲。パスワードの残り)** Q67 の修正のあとのコードレビュー(2026-10-18)で見つかった。Q65 の修正で入った問題(develop では起きない)
  - 例: `password=https://u:s3cret@<aws_host_1>.ap-northeast-1.rds.amazonaws.com/`、`"password": "https://u:s3cret@<ipv4_private_1>:5432/app"`、`password=https://<uuid_1>:s3cret@db-host/app`。Q65 の判定は、ユーザーの部分や `@` の直後が置換済みの形でも、URL のパスワードの形として、キー名ベースの値として扱わない。一方、URL のパスワードの規則(`urlPasswordStart`)は、`@` の直後がホスト名の文字であることを求め、ユーザー情報を遡るときはラベルの `>` で止まるので、これらのパスワードを置換しない。**どちらの規則でも置換されず、`s3cret` が出力に残る**(「置換済みの形のため残した」の警告だけが出る)。v1.1 と Q65 の修正前は、値全体がキー名ベースの値として置換された
  - 起きる条件: キー名の値が、パスワードが置換されていない URL で、ユーザーの部分か `@` の直後が置換済みの形(`--types` を変えて流し直したログ、手で一部を置換したログなど)

  - 案 A(推奨): 置換済みの形を読むのは、パスワードの部分が置換済みの形 1 つだけのときに限る(そのときは、ユーザーの部分・`@` の直後も置換済みの形でよい)。パスワードが置換されていない形は、`urlPasswordStart` が真になるもの(URL のパスワードの規則が置換するもの)だけを、この形とする。実装は、判定の後半を `urlPasswordStart` の呼び出しにでき、2 つの判定がずれなくなる

- **Q70(URL のユーザーの部分に `@` を含む形。パスワードの残り)** Q69 の修正のあとのファズテスト(`FuzzHashStable`)の入力 `A://0@0.AA!:0@0` を調べる中で見つかった。段階 5 の URL のパスワードで入った、既存の問題
  - 例: `postgres://myadmin@mydemoserver:s3cret@10.0.0.5:5432/db`、`https://bob@example.com:pw@10.0.0.1/repo`、`redis://default@cache:s3cret@cache-host:6379`。**パスワード(`s3cret`・`pw`)が、置換されずに残る**。ユーザー名に `@` を含む形は、Azure Database for PostgreSQL・MySQL(単一サーバー)の `<ユーザー>@<サーバー名>` や、メールアドレスをユーザー名にするサービスで現れる。RFC 3986 では `@` は `%40` にするが、ログや設定にはそのまま書かれることがある(`%40` の形は、今も検出される)
  - 仕組み: `urlPasswordStart` は、`@` から手前を遡るとき、手前の `@` で止まる。2 つ目の `@` から遡ると `mydemoserver:s3cret` までで止まり、その手前が `://` でないので、URL のパスワードの形にならない。1 つ目の `@` は、ユーザー情報に `:` がないので当たらない。ホストにドットがあれば、`s3cret@mydemoserver.postgres.database.azure.com` がメールアドレスとして置換されるので値は隠れるが、ホスト名の情報が消える(v1.1 までと同じ)。ホストが IP アドレスやドットのない名前だと、どの規則にも当たらない
  - 振り分け: 現実にありうる形で値が残るので、直す側
  - 案 A(推奨): ユーザーの部分に `@` を含めてよいことにする(WHATWG の URL の仕様と同じく、ホストの手前の最後の `@` で、ユーザー情報とホストを分ける)。`@` から手前を遡るときに、手前の `@` を越えて、`://` まで遡る。パスワードは、今までどおり、ユーザー情報の中の最初の `:` より後ろ
    - `postgres://myadmin@mydemoserver:<secret_1>@<ipv4_private_1>:5432/db`、`https://<email_1>:<secret_1>@<ipv4_private_1>/repo` になる(1 つ目の `@` の `bob@example.com` は、今までどおりメールアドレス)。ホストにドットがある形も、ホスト名が残るようになる
    - パスワードに `@` を含む形(`https://u:p@q@host/`)は、パスワードが `p@q` になる(今は `p` で、`q@host` がメールアドレスとして置換される)
    - 遡る長さ: `@` が多い行で、`@` ごとに `://` まで遡ると、行の長さの 2 乗の時間がかかる。同じ範囲(手前の止まる文字から)を遡った結果を覚えて、合計を行の長さ以内に収める(`aws_host` の `hostRunCache` と同じ考え方)
    - `urlPasswordStart` は email の判定(この `@` をメールアドレスとして扱わない)も共用するので、email の側もそろって変わる
    - `A://0@0.AA!:0@0` は、この案で 1 回目から `0` が URL のパスワードとして置換されるので、冪等性の違反も直ると見込む(実装時に確かめる。直らなければ、作り物の入力なので README の限界に書く)
  - 案 B: ユーザーの部分がメールアドレスの形(`bob@example.com`)の場合だけ、`@` を越えて遡る。範囲は狭いが、Azure の `myadmin@mydemoserver`(ドメインに TLD がない)には当たらない
  - 案 C: 直さず、README の限界に書く(ユーザー名の `@` は `%40` にするよう案内する)
  - **回答(2026-10-18)**: 案 A。仕様 4.1(URL のパスワード)・9 章・決定事項 20・11 章、README(限界、変更点)に反映した
