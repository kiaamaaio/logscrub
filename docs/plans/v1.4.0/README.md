# logscrub v1.4.0 実装計画

- 目的: v1.3.0 の性能の低下を戻し、処理が重い機能(#18、#20、#21、#22)を足す前に、処理量を伸ばせる構造にする
- 仕様: [SPEC.md](../../SPEC.md) の 7 章(非機能要件)。検出と置換の結果は変えない
- 前提: v1.3.0 が `develop` にマージされていること。標準ライブラリのみ
- ブランチ: `feature/v1.4.0-perf`(v1.3.0 のマージ後の `develop` から作成)。段階ごとにコミットし、`develop` へは、指示があってから、`/code-review` のあとで AI が PR を作り、人がマージする
- 各段階の完了条件: `./scripts/go test ./...` と `./scripts/go vet ./...` が通ること。段階 3 以降は `-race` も通ること
- 版の完了条件:
  - 3 章の採否の基準を満たす段階だけが残っていること
  - 既存のゴールデンが 1 バイトも変わらないこと
  - `FuzzMaskStable`・`FuzzHashStable`・`FuzzRestoreRoundTrip` を各 90 秒実行して失敗がないこと
  - `-perf` の 2 つのテストが通り、結果を log.md に記録したこと
- 止まる条件: Q の回答待ち、仕様との食い違い、公開のオプションや出力の変更が要るとき、ゴールデンが変わるとき、採否の基準を満たせないとき、同じ失敗を 2 回直せなかったとき
- 未確定事項: [questions.md](questions.md)。回答待ちの項目は推測で実装しない
- 段階ごとの記録: [log.md](log.md)

## 4. 設計の方針

### 4.1 回答の走査(段階 2)

- `AnswerScanner.Scan` は、行に `\` も `&` もなければ、`Format.Scan` に任せる(崩れた形は必ずどちらかを含む)
- それ以外の行と `ScanEscaped` は、ラベルの先頭のバイトを `bytes.IndexByte` で探す。書式の `pre` が空のときは、今の `start` の表のまま

### 4.2 照合器の読み飛ばし(段階 3)

- `literalMatcher` に、語の先頭 2 バイトの同値類の組の表を持たせる。根の状態では、組にならない位置を読み飛ばす
- 1 バイトの語があるときは、根から遷移しないバイトを 1 バイトの表で読み飛ばす
- 結果は変えない。既存の参照実装との乱数テストに、1 バイトの語、行末の語、大文字の語を足す

### 4.3 検出の並列化(段階 4、5)

処理を 3 つに分ける。**連番を振る処理を 1 か所に保つ**ので、連番と restore の対応は変わらない。

```text
読み取り(1 つ) → 検出(ワーカー、複数) → 書き換えと書き込み(1 つ、入力の順)
```

- 読み取り: 行の区切りまでのブロック(既定 256KB)にまとめる。`Read` が返った時点で完全な行があれば、ブロックが埋まるのを待たない
- 検出: `Detector` に `Clone` を加え、検出器を共有して作業領域だけを分ける。`Engine.Det` と `Restore` の引数は変えない
- 書き換え: ブロックの順に `Rep.Append`、`Stats`、`Inspect`、書き込みを行う。行番号の通知もここで数える
- 使い回すブロックは数を固定する(ワーカー数 × 3)。長い行で大きくなったバッファは、使い回さずに手放す
- 経路は 1 つにする。1 コアでも遅くならないので、逐次の経路を残さない(Q95)
- ワーカー数は `GOMAXPROCS` から決め、上限を 8 にする(Q96)

今の動作と同じにすること:

- 行の区切り: LF、CRLF、単独の `\r` は行の中身、末尾改行なしの最後の行、入力ごとの区切り(Q22)、行の長さの上限なし
- 読み取りエラーでは、読みかけの行を処理しない。エラーより前の完全な行は、今と同じように出力する
- 書き込みエラー(`| head` など)では、すべての goroutine を止めてエラーを返す

## 5. 実装の段階

### 段階 0: 確定の反映

- **前提となる確認:** Q94〜Q99 すべて。v1.3.0 のマージ
- **作業:** `feature/v1.4.0-perf` を作る。仕様 7 章に、確定した内容を書く。DEVELOPMENT.md に、処理の構成を書く
- **確かめること:** `scripts/doc-size-check`

### 段階 1: 測定の土台

- **前提となる確認:** なし
- **作業:** `-perf` に、実バイナリの restore、`--mode hash`、語 1000 個の綴りが多様な場合を加える。子プロセスの `GOMAXPROCS` を 1 と 2 にした測定を加える。改善の前の値を記録する
- **確かめること:** `./scripts/go test -run Perf -v ./cmd/logscrub -perf`

### 段階 2: 回答の走査

- **前提となる確認:** Q97
- **作業:** 4.1 節
- **確かめること:** 既存の restore のテスト、`FuzzRestoreRoundTrip` を 90 秒、`BenchmarkRestore` を変更前と v1.2.0 と交互に 4 回。3 章の基準

### 段階 3: 照合器の読み飛ばし

- **前提となる確認:** Q97、Q99
- **作業:** 4.2 節。`BenchmarkLiteralMatcher` に、綴りが多様な語の一覧を加える
- **確かめること:** 参照実装との乱数テスト、5 通りの語の一覧の測定。3 章の基準

### 段階 4: 行のブロックの読み取り

- **前提となる確認:** Q95、Q98
- **作業:** `internal/stream` に、完全な行のブロックを返す読み取りを加える。この段階では、`Engine` は変えない
- **確かめること:** `Reader.Next` との一致を、乱数の分割で確かめる(改行コード、末尾、64KB・256KB をまたぐ行、1 バイトずつ返す `Read`、読み取りエラー、途中で止まる入力)

### 段階 5: `Engine` の並列化

- **前提となる確認:** Q95、Q96
- **作業:** 4.3 節。`Detector.Clone`、`Engine.Run` の 3 段の処理
- **確かめること:**
  - テストの中に残す逐次の参照実装と、ワーカー数 1・2・4・8 で、出力、`Stats`、通知の行番号が一致すること
  - 複数の入力、`--source`、1MB の行、読み取りエラー、書き込みエラーのあとに goroutine が残らないこと
  - `CGO_ENABLED=1 ./scripts/go test -race ./...`
  - 既存のゴールデンが変わらないこと。実バイナリの速度と最大メモリ。3 章の基準

### 段階 6: 採否の判断

- **前提となる確認:** なし
- **作業:** 段階 2〜5 の結果を基準と比べ、残すものと見送るものを log.md に書く。見送るときは、該当の段階を戻す。必須の段階 4、5 を見送る場合は、段階 2、3 だけで版を出すかをユーザーに確認する。何も残らない場合は、調査の結果だけを残し、版を作らない
- **確かめること:** 判断をユーザーに報告して、確認を受ける

### 段階 7: 仕上げ

- **前提となる確認:** なし
- **作業:** ファズテストを各 90 秒。`-perf` の測定。README の性能の表(測ったコア数を書く)、CHANGELOG、[開発の資料の 3.4 節](../../development/performance.md)、`docs/plans/README.md` の状態
- **確かめること:** 版の完了条件すべて。`./scripts/doc-size-check`
- **完了後の報告:** v1.3.0 の Release に添付ファイルがない件で、作成のコマンドをユーザーに示す(2026-11-01 の指示。AI は実行しない)
