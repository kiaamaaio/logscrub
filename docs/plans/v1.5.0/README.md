# logscrub v1.5.0 実装計画

- 目的: 残りやすい値(ホームディレクトリのユーザー名、PEM の秘密鍵)を伏せ、出力の確認(`--review`)と、AI にファイルを読ませる使い方(`--out-dir`)を支える
- 対象の issue: [#13](https://github.com/kiaamaaio/logscrub/issues/13)、[#14](https://github.com/kiaamaaio/logscrub/issues/14)、[#16](https://github.com/kiaamaaio/logscrub/issues/16)、[#19](https://github.com/kiaamaaio/logscrub/issues/19)
- 仕様: [SPEC.md](../../SPEC.md) の 2 章、[4 章](../../spec/detect.md)、[4.1](../../spec/secret.md)、[6 章](../../spec/modes-cli.md)、7 章、[9 章](../../spec/acceptance.md)。新しい節 4.8。決定事項は 28 から足す
- 前提: v1.4.0 のあとの `develop`。標準ライブラリのみ。既定の動作が変わるので、版は v1.5.0 とする(v1.2.0 と同じ扱い)
- ブランチ: `feature/v1.5.0-pem-review`(`develop` から作成)。段階ごとにコミットし、`develop` へは、指示があってから、`/code-review` のあとで AI が PR を作り、人がマージする
- 各段階の完了条件: `./scripts/go test ./...` と `./scripts/go vet ./...` が通ること。段階の完了時に、コミットのあとに止まり、差分と結果を報告する
- 版の完了条件:
  - 既存のゴールデンが 1 バイトも変わらないこと
  - `FuzzMaskStable`・`FuzzHashStable`・`FuzzRestoreRoundTrip` を各 90 秒実行して、[振り分けの基準](../../DEVELOPMENT.md)で直す失敗がないこと
  - `-perf` の 2 つのテストが通り、結果を log.md に記録したこと
  - 速度が 4.1 節の基準を満たしていること
- 止まる条件: Q の回答待ち、仕様との食い違い、Q の範囲を超える公開のオプションや出力の変更、既存の期待値やゴールデンの変更、速度の基準の「止まる」に当たるとき、同じ失敗を 2 回直せなかったとき
- 未確定事項: [questions.md](questions.md)。回答待ちの項目は推測で実装しない
- 段階ごとの記録: [log.md](log.md)

## 3. 設計の方針

### 3.1 `user_path`(段階 1)

- 値はユーザー名の部分だけ(`/home/<user_path_1>/proj/app.py`)。`/home/yamada` と `/Users/yamada` は同じ値で、同じラベルになる。`restore` は今の仕組みで戻る
- `detect` に検出器 `userPathFinder` を足す(`userpath.go`)。形の表と除外の名前は、形の表として持つ。手がかりがない行は、すぐ戻る
- 種別の追加: `kind.go`、`label.Types`(`NumTypes` は 13)、`cli/types.go`、`LabelType`。`--stats` の並びは `custom` の次
- 対象外の名前は、固定の一覧(Q102)。照合の大文字・小文字は、形の規則に従う(Windows の形だけ区別しない)
- 置換済みの形: `<user_path_1>` は文字の条件で候補にならない。`user_path_<hex>` は、保護範囲の同じ長さで勝つ。どちらもテストで確かめる
- `<user_path_N>`、`user_path_<12 桁の 16 進数>` の形の文字列は、新たに置換済みの形になる。CHANGELOG に書く(v1.3.0 の `host`・`custom` と同じ)

### 3.2 PEM の秘密鍵(段階 2)

検出は行ごとに独立でなければならないので、状態は**読み取りの段だけ**に持つ(Q98、DEVELOPMENT.md 3.3 節)。

```text
読み取り: ブロックごとに印を探し、本文の行の範囲を block に記録する(状態はここだけ)
検出: 本文の行は Detector の本文用の入口で、それ以外は Find で処理する
書き換え: 今のまま(Rep.Append、Stats、通知)
```

- 読み取りは、ブロックに印がなく、ブロックの外の状態なら、`bytes.Index` 1 回で終える。状態の中では、ブロックの行を調べる
- `readBlocks` の状態は、入力ごとに戻す。行が入力ごとに区切られるので(Q22)、`--source` の複数指定と `mask a b` は同じ結果になる
- `Detector` の本文用の入口も、`--allow` と保護範囲を通す。本文の行が `<secret_1>` なら置換しない(冪等性)
- `secret` が無効なら、読み取りで印を探さない
- 1 行の形(Q107)は、`secret` の検出器の新しい形として、行の中で閉じて実装する。状態は要らない
- 印が欠ける既存の出力(`private_key=<secret_N> PRIVATE KEY-----`)は変えない。読み取りは元の入力で印を探すので、後ろの本文は伏せられる
- 行の途中から切り出したログ(BEGIN のない本文)は、検出できない。LIMITATIONS.md に書く

### 3.3 `--out-dir`(段階 3)

- `Engine` は変えない。`Engine.Run` をファイルごとに呼び、`Rep` と `Stats` を引き継ぐ。出力先だけが変わるので、連番と通知の行番号は `mask a b` と同じ(行番号は通しのまま)
- 手順: 全部の入力を確かめる → 書き出し先を求めて重なりと既存のファイルを確かめる → 1 ファイルずつ開いて、`O_EXCL` で作って書く。入力を一度にすべて開いたままにしない(ファイル数が多いと、開ける数の上限に当たるため)
- 途中のエラーでは、今回書いたファイルを消す
- `--stats`、`--fail-on-detect`、`--mode hash` は、全部のファイルの合計で今と同じように働く
- README に、AI エージェントに読ませる使い方と、`restore --source` を同じ順に並べることを書く

### 3.4 `--review`(段階 4)

- `Engine` に、任意の `Review` を足す。`nil` なら、今の経路と同じ。`writeLine` で、置換した箇所と置換しなかった箇所を分けて出力する
- 置換しなかった部分の制御文字を見える形にし、Q109 の規則で怪しい語に色を付ける。ブロックの検出のワーカーには足さず、書き換えの段だけで行う
- 怪しい語の件数と行番号は、`Stats` の `Kept` と同じ形で数え、値は stderr に出さない
- `--review` の出力は、改行コードなどの保持の対象にしない。確認専用と usage と README に書く

## 4. 実装の段階

### 4.1 速度の基準

新しい検出には、避けられない費用がある。そのため、変更前との差を合否にせず、確認のきっかけにする(2026-11-01 に見直した)。比べるのは前の段階のコミットで、同じ合成ログを、同じマシンで交互に測る。

| 対象 | 基準 | 満たさないとき |
|---|---|---|
| 仕様 7 章の目標 | 50MB/s 以上 | 止まる |
| 使っていない機能の費用(`--review`・`--out-dir` なしの経路、PEM の印のないログの読み取りの段) | 測定のばらつきの範囲 | 原因を直す。直せなければ止まる |
| 既定で動く検出の費用 | 前の段階から 5% 以内 | 止まって、原因と数値を報告し、受け入れるかの判断を受ける |

5% を超えた費用は、原因を特定できていて、機能の内容から避けられないものなら、受け入れてよい。受け入れた値を、次の段階の比較の基準にする。

### 段階 0: 確定の反映

- **前提となる確認:** Q100〜Q111 すべて
- **作業:** `feature/v1.5.0-pem-review` を作る。合成ログと `-perf` の、変更前の基準値を測る。確定した内容を仕様(2、4、4.1、4.8、6、7、9、10、11 章)に書く。`docs/DEVELOPMENT.md` の Q の範囲を更新する。3 章の設計を回答に合わせて直す
- **確かめること:** `scripts/doc-size-check`。`docs/DEVELOPMENT.md` が目安を超えるなら、書き足す前に分割の案を示す

### 段階 1: `user_path`(#13)

- **前提となる確認:** Q100〜Q103

### 段階 2: PEM の秘密鍵(#14)

- **前提となる確認:** Q104〜Q107

  - ブロックの境目(256KB)をまたぐ鍵、LF / CRLF、末尾改行なし、複数の入力、END のない入力

  - mask → restore で 1 バイトも違わないこと。mask・hash の 2 回目で変わらないこと
  - `CGO_ENABLED=1 ./scripts/go test -race ./...`

### 段階 3: `--out-dir`(#19)

- **前提となる確認:** Q110、Q111

### 段階 4: `--review`(#16)

- **前提となる確認:** Q108、Q109

- **確かめること:**
  - 色の指定を除いた出力が、通常の mask の出力と同じこと(制御文字のない入力で)
  - `--review` なしの出力が変わらないこと。速度(4.1 節)
  - 制御文字を含むログで、表示を隠せないこと。`NO_COLOR`
  - 既存の testdata と合成ログで、怪しい語の件数と誤検出を log.md に記録する
