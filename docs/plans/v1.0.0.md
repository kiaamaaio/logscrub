### 段階 2: 検出の枠組み(`label`、`detect` の骨組み) — ✅ 完了(2026-10-11)

- `label.ParseFormat` / `Append` / `Scan`、`label.ScanHashed`
- `detect.ParseTypes`、`Kind` / `Match`、重なりの解決、置換済みの値の除外、`--allow` と IP の区別による除外の差し込み口
- 検出器はテスト用の偽物(固定の範囲を返すもの)で、重なりの規則だけを先に検証する
  - 長いほうが勝つ / 同じ長さは優先順位 / 一部だけ重なる / 3 つ以上が連鎖して重なる / 同じ種別・同じ長さ
  - 置換済みラベル・hash 出力形との重なり(DEVELOPMENT.md 3.2 節の方針)
- ベンチマークの枠(`BenchmarkFind`、合成ログの生成器)をこの時点で用意し、以降の段階で毎回測る
- 前提となる確認: Q1、Q2、Q10、Q11、Q12(すべて確定済み)

**実装メモ・気づいた点**

- 実装: `internal/label/{format,hashed}.go`、`internal/detect/{kind,detector}.go`、`internal/synthlog/synthlog.go`。テストは各パッケージの `*_test.go`
- `Detector.Find` の戻り値は `([]Match, int)`(この計画の案は `[]Match` のみ)。2 つ目は Q31 の件数で、置換済みの形のため残した範囲のうち、重なりの解決で残ったものの数。段階 7 以降の `Engine` が、件数と行番号を集計して stderr に出す
- `finder` に `may` / `lineHint` は入れなかった。段階 3 の測定で、各検出器が `IndexByte` で手がかりを探す方式のほうが約 14 倍速かったため、`find` の中で前処理する方式にした(DEVELOPMENT.md 2 章、3.4 節)
- 重なりの解決は、塊ごとに解決する方式にした(DEVELOPMENT.md 3.1 節)。`TestManyDisjointCandidates`(10 万件)と、乱数 3000 通りの参照実装との一致テストで確認
- 「保護範囲」の数え方(Q31): 置換済みの形の文字列は、競合する候補がなくても数える(`<email_1>` だけの行でも 1 件)。仕様 9 章「置換済みの形の文字列を含む入力では、件数と行番号が stderr に通知される」に合わせた。競合する候補に負けて置換された場合は数えない。`--allow` で残したものは数えない
- `--allow` は、検出器が見つけた候補のテキストとの完全一致で判定する(候補にならない文字列は対象外)。大文字・小文字は区別する
- `label.ScanHashed` は、`hash_<hex>@ドメイン` の範囲をドメインの末尾までとする。ドメインの形(`([A-Za-z0-9-]+\.)+[A-Za-z]{2,}`、末尾の `.` を含めない)は `label` 内の `domainEnd` が持つ。**段階 3 の email 検出器は、この形と範囲が一致するように作り、`hash_<hex>@ドメイン` が検出対象外であることを、検出器側のテストでも確認する**(範囲が保護範囲より長いと、保護範囲が負けて再ハッシュされるため)
- `KindSet` のゼロ値は「`DefaultKinds`」として扱う(`--types` が空になることはないため)
- `New` で、`HashLen`(8〜64、Q21)、`UUIDVersions`(1〜8)、`IPScope` を検証する。CLI のオプション解析(段階 10)は、文字列から値を作るところだけを持てばよい
- 追加した `synthlog`: Q29 の条件(200 バイト前後、約 30% の行に検出対象、`LongLineEvery` ごとに 1MB の JSON 行)の合成ログを、同じ設定なら同じ内容で作る。`Stats` で内訳が分かる。検出対象でない行には `@` や IP アドレスを入れない

**仕様・計画で決まっていなかったため、文面どおりに実装した点(異論があれば指摘してほしい)**

- `--types` の名前は、完全一致のみ(`Email`、`email, uuid` の空白、`email,` の空の要素は、存在しない種別名としてエラー)
- `{type}` / `{n}` の前後にリテラルがない書式(`{type}_{n}`、`{type}{n}`)では、`my_email_1` の中の `email_1` もラベルとして扱う(単語の境界は見ない)。このため、`client_secret_1` のような本物の値が保護範囲になりうる。既定の `<{type}_{n}>` では起きない
- hash 出力形の前後の文字は、英数字かどうかだけで判定する(Q10 の確定内容どおり)。`_` は英数字に含めないので、`my_email_<hex>` も保護範囲になる

**ベンチマーク(`BenchmarkFind`)**: 検出器がまだないため、置換済みの形の走査と重なりの解決だけの数値(基準値)。後の段階の数値と比べる

### 段階 3: email — ✅ 完了(2026-10-11)

- 検出器(TLD は英字 2 文字以上。`pass@10.0.0.1` を拾わない)
- 前処理: 行に `@` がなければ呼ばない
- 前提となる確認: Q5(正規表現の境界)(確定済み)

**実装メモ・気づいた点**

- 実装: `internal/detect/email.go`(`emailFinder`)、`internal/label/email.go`(`EmailDomainEnd`、`IsEmailLocalChar`、`IsHashedLocalPart`)
- 規則(Q5): ローカルパート `[A-Za-z0-9._%+-]+`、ドメイン `([A-Za-z0-9-]+\.)+[A-Za-z]{2,}`、後ろに `[A-Za-z0-9-]` が続かない。大文字・小文字は区別しない。非 ASCII は英数字でない扱い
- **正規表現のまま実装した(Q2)**。`(...)(?:[^A-Za-z0-9-]|$)` の正規表現を、最初の `@` のローカルパートの先頭から当て、一致のたびにその終端から次の `@` を探す。`@` のない行は `IndexByte` 1 回で終わる
- Q2 の手順(まず正規表現で測り、50MB/s に届かない場合だけ手書きに置き換える)のため、手書きの走査(`anchorScan`)は**置き換え候補としてテスト側に置いた**。2 つの実装が、乱数 3 万通りで一致することを確認している。置き換える場合は、この関数を本番に移し、正規表現版をテストの参照に回す
  - 実装の順序の訂正: 最初は手書き版を本番に置いていたが、測定の結果、正規表現版でも 50MB/s を大きく超えたので、手順どおり正規表現に戻した
- `hash_<hex>@ドメイン` は、検出器側でも対象外にした(ローカルパートが `hash_` + 小文字の 16 進数 `HashLen` 桁のもの)。`label.ScanHashed` の保護範囲と同じ範囲を指すことを、`TestHashedLocalPartRangesAgreeWithScanHashed` で確認している。ドメインの終端は、検出器の正規表現と `label.EmailDomainEnd`(保護範囲側)の 2 か所に書かれているため、このテストと乱数テストで常に一致を確認する
- `hash_<hex>@ドメイン` の検出器側の除外は、`Detector` を通すと「置換済みの形として残した」件数(Q31)に数えられる(保護範囲に残るため)
- `detect.New` を、検証・既定値の適用(`normalize`)→ 検出器の構築、の順に整理した。検出器が `HashLen` を知る必要があるため
- 前処理の方式を確認した(DEVELOPMENT.md 3.4 節): 1 回の走査でビット集合を作る方式は約 0.95GB/s、`@` `:` `=` `_` の `IndexByte` 4 回は約 13GB/s。ヒントの集合は採用せず、各検出器が自分の手がかりを探す

**仕様・計画で決まっていなかったため、文面どおりに実装した点(異論があれば指摘してほしい)**

- 先頭の `.` や `-` も、ローカルパートに含める(`.user@example.com` 全体が一致する)。Q5 の文字クラスどおり
- `https://user:pass@example.com/` では、`pass@example.com` がメールアドレスとして一致する(URL の userinfo だが、形式は一致する)。受け入れ基準にあるのは `pass@10.0.0.1` を拾わないことだけ
- 前の一致の終端の `@` は、次のメールアドレスのローカルパートにならない。`user@example.com@evil.example.org` は `user@example.com` だけが一致し、`@evil.example.org` は残る(正規表現の左から順の一致と同じ)
- ドメインが英字だけのラベルで終わらない場合は、そこまでの最後の英字だけのラベル(2 文字以上)で終える。`user@a.bc.com-x` は `user@a.bc` が一致し、`.com-x` は残る(`user@example.com-` は一致しない)
- 引用符つきのローカルパート、国際化ドメイン(`user@例え.jp`)、非 ASCII のローカルパートは、Q5 のとおり対象外(`名前@example.com` は検出されない)

### 段階 4: ipv4 / ipv6 — ✅ 完了(2026-10-11)

- 候補の切り出し → `netip.ParseAddr` → 区別(global / private / 特殊)の判定 → `--ip-scope` の適用
- 前後の文字の条件、ポート付き・`[...]`・CIDR、IPv4 埋め込み(埋め込まれた IPv4 で区別を判定)
- 前処理: IPv4 は `.` と数字、IPv6 は `:` を含む行だけ
- 前提となる確認: Q6、Q7、Q8(確定済み)

**実装メモ・気づいた点**

- 実装: `internal/detect/ip.go`(`classify`、`ipv4Finder`、`ipv6Finder`)。`--ip-scope` と特殊アドレスの除外は、段階 2 の `Detector` が行う(検出器は区別を `Class` に入れて返すだけ)
- 区別(`classify`): 特殊 = `IsUnspecified` / `IsMulticast` / `255.255.255.255`、private = `IsLoopback` / `IsPrivate` / `IsLinkLocalUnicast` / `100.64.0.0/10`、それ以外 = global。仕様の「上記以外は global」のとおり、予約済みの範囲(`240.0.0.0/4`、`198.18.0.0/15`、`0.0.0.0/8` のうち `0.0.0.0` 以外、`2001:db8::/32` など)も global になる
- IPv4-mapped(`::ffff:a.b.c.d`)は、`Unmap` して IPv4 として区別する(Q8)。埋め込み先が特殊なら、IPv6 全体を置換しない。`::a.b.c.d`、`64:ff9b::/96` は IPv6 のアドレスとして判定する
- **IPv4**: 正規表現 `[0-9]{1,3}(\.[0-9]{1,3}){3}` で候補を拾い、前後の文字の条件と `netip.ParseAddr`(0〜255、先頭 0 の除外 = Q7)で確認する
  - 前処理(`ipv4WindowStart`): 数字に挟まれた `.` が 3 つ連続する箇所の手前から、正規表現を当てる。タイムスタンプなどの `.` では当てない。前処理は必要条件だけを見るので、結果は変わらない(前処理なしの正規表現版 `refIPv4` と、乱数 4 万通りで一致)
  - 前処理なしでは約 83MB/s、前処理ありでは約 2.25GB/s。**手書きの走査への置き換え(Q2)は不要だった**
- **IPv6**(精度重視に改訂。SPEC 4.3、決定事項 14): `:` を手がかりに、16 進数・`:`・`.` の連なりを伸ばし(ここが窓の切り出し)、`trimIPv6Run` で整えてから `:` を 2 つ以上含むものを `netip.ParseAddr` で確認し、**割り当て済みの範囲(`assignedIPv6`)だけ**を検出する
  - 整え方(D+C): 前後の `.` を外す → 先頭・末尾の単独の `:` を外す(`src:2001:db8::1`、`2001:db8::1: refused`)→ 前(後ろ)が英字・`_` なら、その端のグループを最初(最後)の `:` まで切り離す(`tcp6:fe80::1` の `6`、`std::string` の `d`)
  - 割り当て済みの範囲(B): `2000::/3`、`fc00::/7`、`fe80::/10`、`ff00::/8`、`64:ff9b::/96`、`::1`、`::`、IPv4-mapped。それ以外(`::/8`、`100::/8` など)は検出しない。`::10.0.0.1` は IPv6 としては検出されないが、IPv4 部分は IPv4 として検出される
  - 経緯: 段階 4 の最初の実装(仕様どおり)では、`std::string` → `d::`、`fmt::Error` → `::E` などが IPv6 として誤検出され、`src:2001:db8::1` は `c:2001:db8::1` と範囲がずれた。実測(使い捨てのテスト)で、現状 = 誤検出 15 / 22・見落とし・範囲ずれ 4 / 23 に対し、D+B+C は 誤検出 0 / 22・見落とし 1 / 23(`::10.0.0.1` のみ)だった。2026-10-11 に利用者の判断で改訂した
  - 連なりの切り出しは文字クラスだけで、正規表現と書き分ける意味が小さいため、最初から手書きで実装した(Q2 の「まず正規表現で測る」順序には従っていない)。正規表現による別実装 `refIPv6`(整理の規則と範囲の一覧は、プレフィックスの一覧で書いた)をテストに置き、乱数 6 万通りで一致を確認している
  - `ParseAddr` を呼ぶ前に、`::` を含む / `:` が 7 つ / IPv4 埋め込みで 6 つ、の形でないもの(時刻 `12:34:56`、MAC アドレス)と、45 文字を超えるものを飛ばす
- ゾーンの文字は、`[A-Za-z0-9_-]` と、その間の `.`(`%br-lan.100`)。文末の `.` は含めない。`%` の後にゾーンがなければ、アドレス部分だけ
- 段階 3 のテスト `TestDetectorDoesNotTreatUserinfoAtIPAsEmail` を直した。`DefaultKinds` で「何も検出されない」ことを期待していたが、IP 検出器が加わったので `10.0.0.1` が検出される。テストの目的(email として扱わない)に合わせて、email だけを有効にして確認する形にした。既定の種別での結果は `TestUserinfoWithIPv4` で確認する

**残る限界(README に書く)**

- `A::B` や `2001::x` のように、割り当て済みの範囲の形をしたコードの記号は、IPv6 として検出されうる(`TestIPv6CodeSymbolsAreNotAddresses` に、検出されないことを確認した記号の一覧がある)
- 割り当てのない範囲の IPv6(`::10.0.0.1`、`100::1` など)は、検出されない
- 後ろが英字・`_` と癒着した IPv6(`2001:db8::1xyz`)は、アドレスとして扱わない(`2001:db8::1abc` は、`abc` が 16 進数なのでアドレスの一部)

### 段階 5: secret — ✅ 完了(2026-10-11。同日、精度重視と JSON の文法の保持のために改訂)

- 固定形式(AWS、GitHub、Slack、Stripe、Google、`sk-`、JWT)、`Bearer` / `Basic`、キー名ベース
- 前処理: 固定形式は接頭辞のリテラル(`AKIA`、`ASIA`、`ghp_`、`xox`、`eyJ` など)を `bytes.Index` で探してから正規表現を当てる。キー名ベースは `=` か `:` を含む行だけ
- 前提となる確認: Q13、Q14、Q15、Q16、Q17(確定済み。Q13・Q17 は、改訂で内容を変えた。下の「改訂」を参照)

**実装メモ・気づいた点**

- 実装: `internal/detect/secret.go`(`secretFinder`)。固定形式とキー名ベース(Authorization を含む)の 2 つの規則の候補をまとめて返し、重なりは `Detector` が解決する(同じ範囲の候補が複数出ることがある。解決で 1 つになる)
- **固定形式**: 接頭辞のリテラル(`AKIA` `ASIA` `AIza` `gh` `github_pat_` `xox` `sk` `rk` `eyJ`)を、次の出現位置を持ちながら `bytes.Index` で探し、見つかった位置に、アンカー付きの正規表現(`^(?:...)`)を当てる。前後が英数字でないこと(Q14)は、呼び出し側で確認する。一致を拒否した位置は、次の位置から探し直す
  - `github_pat_` は、先頭が `gi` で `gh` に当たらないため、接頭辞を別に持つ(最初の実装で漏れていた。乱数テストでなく表のテストで見つかった)
  - 署名部が空の JWT(`alg: none`)は、区切りの `.` までを範囲とする
- **キー名ベース**: `=` と `:` の次の出現位置を持ちながら探し、各区切りの手前(空白、閉じ引用符を除く)の英数字と `_` `-` `.` の連なりを、キー名として照合する
  - 照合: キー名の末尾 15 バイトを、小文字にし、`-` `.` を `_` にそろえ、camelCase の境目に `_` を入れてから(`normalizeKeyTail`)、13 種の名前(と `authorization`)の末尾の単位と比べる。末尾が `d` `t` `y` `n` のものだけを比べる
  - 値の位置の整理: 区切りの後の空白を飛ばし、引用符(`"` `'`、または `\"`)で始まれば内容の開始を引用符の次にし、そこが `Bearer ` / `Basic ` で始まれば、その後ろの値(token68)だけを返す。`Basic` は、base64 として解読でき `:` を含む場合に限る
  - 値の範囲: 引用符で始まれば閉じ引用符の手前まで(`\` の次の文字は値の一部。閉じ引用符がなければ行末まで = Q16)。`\"` で始まれば次の `\"` の手前まで。それ以外は `bareValueEnd`(空白・`&` `,` `;` `}` `]` `)` `"` `'` と、JSON のエスケープ `\"` `\'` `\n` `\r` `\t` `\u0026` の手前。`\\` は 1 文字)
  - 値の範囲だけを返す(キー名・区切り・引用符は残る)。区切りの前後の空白は任意個(Q15)
- 置換済みの形(`<secret_1>`、`secret_3f9a1c0b7d2e`)を値に持つものは、段階 2 の保護範囲が、同じ範囲で勝つため、再検出されない(`password=<secret_1>`、`Authorization: Bearer <secret_1>`、`"api_key": "<secret_1>"` と、`[{type}-{n}]` 書式で確認)
- 検出器の構成は、Q2 の順序(まず正規表現で測る)のうち、固定形式だけが正規表現で、キー名ベースは手がかりの周辺を手書きで見ている。測定した結果(下の記録)は目標を大きく超えるため、これ以上の置き換えや最適化はしていない。**正規表現による別実装 `refSecrets`(固定形式とキー名ベースの両方。camelCase は正規表現の置換で書いた)をテストに置き、乱数 6 万通りで一致を確認している**

**改訂(2026-10-11): 精度重視と、JSON などの文法を壊さないこと**(SPEC 4.1、決定事項 15)

最初の実装(仕様と Q13〜Q17 のとおり)で、次の問題が分かり、利用者の判断で、精度重視と JSON の文法の保持を基準に改めた。

| 問題 | 最初の実装 | 改訂後 |
|---|---|---|
| camelCase のキー(`accessToken`、`clientSecret`、`sessionId`)が検出されない | 区切りは `_` `-` `.` だけ | 小文字・数字から大文字への変わり目と、大文字の連なりの終わり(`APIKey`)も区切り。`maxTokens`、`tokenCount`、`PGPASSWORD` は、対象外のまま |
| `"token": 12345`、`"password": null`、`"token": {"a":1}` で、JSON が壊れる(Q17) | クォートなしの規則で置換 | キー名が引用符で囲まれた形(JSON、辞書)では、値が文字列のものだけ置換する。数値・`true`・`false`・`null`・`{`・`[` は置換しない。引用符なしの `{` `[` で始まる値も置換しない |
| `{"msg":"password=abc"}` で、閉じ引用符を巻き込んで JSON が壊れる | 値は空白などの手前まで | 引用符なしの値の終端に、`"` `'` `)` を加える |
| ログに埋め込まれた JSON(`\"password\":\"abc\"`)で、キーが見つからない・`\` を巻き込んで壊れる | 対象外 | キー・値の引用符が `\"` でもよい。引用符なしの値は、`\"` `\n` `\t` `\u0026` などの手前の `\` で終わる |
| 文章中の `Bearer token is ...` の `token` が置換される(Q13) | `Bearer` / `Basic` を、どこでも対象にする | キー名(`Authorization`、`Proxy-Authorization`、または対象のキー名)の値が方式名で始まる場合に限る。`token: Bearer abc` は `abc` だけを置換する |

- 変えなかった点: 引用符なしの値が空白で終わること(`password: my secret phrase` は最初の語だけ)。行末まで伸ばすと、`token=abc user=bob` の `user=bob` まで巻き込み、精度と構造を損なうため。README の限界に書く
- 検証: 乱数で作った JSON 4,000 件(入れ子、ログに埋め込まれた JSON、メールアドレス・IP アドレス・各種トークンを含む文字列)で、検出した範囲を別の文字列に置き換えても JSON として妥当なままであることを確認している(`TestDetectedRangesKeepJSONValid`)。この性質テストが、`\"` の手前の `\` を巻き込む問題を最初に見つけた

**残る限界(README に書く)**

- 引用符なしの値は、空白・`&` `,` `;` `}` `]` `)` `"` `'` で終わる。空白を含む値(パスフレーズ)や、これらの文字を含む値は、途中までしか置換されない
- JSON の数値だけのトークン(`"pin": 123456`)は、文法を壊さないため置換されない
- 文章中の `token: expired` の `expired` は、置換される(キー名のあとの区切りと値の形で、文章と区別できない)
- `Basic` は、base64 として解読でき `:` を含む値だけ。形式の違う値は、置換されない

  - ファズテストは、60 秒 × 4 ラウンド(合計約 940 万回)で、この性質の違反が見つからなかった

### 段階 8: hash(`transform.Hasher`、`LoadKey`) — ✅ 完了(2026-10-11)

**実装メモ・気づいた点**

- **`Hasher`**(`Replacer`): HMAC-SHA256 に渡すのは、値のバイト列だけ(`local` はローカルパートだけ。種別名は含めない。正規化しない)。出力は、小文字の 16 進数の先頭 `hashLen` 桁。`<種別>_<hex>`(IP は区別込み。例: `ipv4_private_dca2f4f38564`)、`local` のメールアドレスは `hash_<hex>@ドメイン`。`NewHasher` は、鍵が空・桁数が 8〜64 の範囲外・`EmailHash` が不明、ならエラー(0 は既定の 12)。エラーに鍵を含めない
  - 別マシンでも同じ出力になることは、Python の `hmac` で別に求めた値(`TestHashKnownAnswers`、`TestHashLength`)で確認した
- **`LoadKey`**: `--key-file` を優先し、末尾の改行(`\n` または `\r\n`)を 1 つだけ除く。ファイルが読めない場合は、環境変数に切り替えずに、エラーにする(意図しない鍵で変換しないため)。空の鍵はエラー。環境変数 `LOGSCRUB_KEY` は、そのまま(改行は除かない)
- **Engine は、mask と同じものを使う**(`Replacer` を差し替えるだけ)。hash モードでは、`detect.Options.HashLen` を `--hash-length` と同じにする必要がある(置換済みの hash 出力形を認識する桁数)。mask と restore は、常に既定の 12(Q10)
- 受け入れ基準: `--email-hash local` が `hash_<hex>@example.com` になり再度流しても変わらない、`full` で全体が置換される、`password=secret_3f9a1c0b7d2e` が再ハッシュされない、鍵が未設定ならエラー(`LoadKey`)、を `hash_test.go`・`key_test.go` で確認した。CLI の終了コードは、段階 10 で確認する

**冪等性のテストで見つけた不具合と、仕様の追記**

- ファズテスト(`FuzzHashStable`)が、`0@0.AA@0.AA` のような、`@` が続く入力で、非冪等を見つけた。1 回目: 先頭の `0@0.AA` だけが email として置換され、`email_<hex>@0.AA` になる。2 回目: `email_<hex>` に `@0.AA` が続くので、全体が 1 つのメールアドレス(ローカルパート `email_<hex>`)として再検出され、再ハッシュされる。実在しうる形(`ssh user@example.com@bastion.example.org` のような、踏み台経由の表記)

- **ファズテストの性質の見直し(隣接の範囲)**: `0@0.AA:::1`(hash)と `::1:1.0.0.0`(mask)が見つかった。どちらも、置換によって、ラベルの 16 進数と連なっていた区切りが切り離され、ラベルの 1 文字隣(`:` を挟む)の値が、新しく検出できるようになる現象で、段階 7 で見つけた「置換で文脈が変わる」と同じ種類。ファズテストの「ラベルに隣接する」の範囲を、間が 1 バイト以内に広げた(mask と hash で、共通の `checkSecondPass` にした)
- 保存されたファズの入力(`internal/transform/testdata/fuzz/`)は、回帰テストとして残す
- ファズテスト: 修正後に、hash(`local` と `full`)が 91 秒、mask が 61 秒、違反が見つからなかった(段階 7 の分と合わせて、合計 1,000 万回以上)
- 性能: `BenchmarkEngineHash` は、`BenchmarkEngineMask` と同程度(HMAC の計算が増えるが、連番の map がなくなる)

## 5. 未確定事項(仕様の曖昧な点・矛盾している点)

推測では埋めず、回答をもらってから該当する段階に入る。「案」は判断材料としての提案で、採用は回答後。

**2026-10-11: Q1〜Q31 はすべて案どおりで確定。** Q31 は SPEC.md(6 章、7 章、9 章「オプション」)にも反映済み。

### 枠組み・冪等性

- **Q1(冪等性の範囲)** 置換済みの形の文字列を「その範囲は置換しない」とするのか、「それと重なる候補はすべて捨てる」とするのか。後者は `"password": "<secret_1> 本物の値"` で本物の値が残る。
  - 案: 前者(DEVELOPMENT.md 3.2 節の、保護範囲が最優先の候補として重なりの解決に参加する方式)
- **Q2(正規表現以外の実装)** 性能が足りない場合に、正規表現を手書きの走査に置き換えてよいか(判定結果は正規表現版と一致させる)。
- **Q10(hash 出力形の桁数・矛盾)** 4 章の除外対象 `<種別>_<16 進数>` の桁数が未定義(5.2 節の `hash_` 側は `--hash-length` 桁と明記)。任意の桁数にすると、mask モードでも `password=secret_abc123` のような本物の値(`abc123` は 16 進数)が置換されなくなる。また `--hash-length` 桁とすると、**restore には `--hash-length` がない**ため、mask 時に `--hash-length` を変えると restore で連番がずれる。
  - 案: 桁数は `--hash-length` に限定。hash 専用オプション(`--hash-length`、`--email-hash`、`--key-file`)を mask モードで指定したらエラーにして、mask モードでは常に既定の 12 桁で除外する(restore も 12 桁)
- **Q11(除外と重なりの解決の順序)** `--allow`、特殊アドレス、`--ip-scope` 外の候補を、重なりの解決の**前**に外すか**後**に外すか。
  - 前に外す場合: `--ip-scope private` で `api_key=203.0.113.5` は secret として置換される(同じ長さで IP が優先されるが、IP は対象外なので外れ、secret が残る)。`token=0.0.0.0` も secret として置換される。ただし `--allow ::ffff:10.0.0.1` では、末尾の `10.0.0.1` だけが置換される
  - 後に外す場合: 上の 2 例は IP が勝ったうえで置換されず、値がそのまま残る
  - 案: 除外の理由で分ける。特殊アドレスと `--ip-scope` 外は**前に外す**(その範囲を他の種別が置換できるようにする。見逃しを減らす側)。`--allow` の値は保護範囲と同じく**重なりの解決に加え、勝てばそのまま残す**(利用者が「この文字列は残す」と明示したものなので、`--allow ::ffff:10.0.0.1` で一部だけ置換されることを避ける。より長い候補に含まれる場合は、長いほうが勝って置換される)
- **Q12(`--mask-format` の制約)** `{type}` / `{n}` が 2 回以上現れる書式、改行を含む書式、`{` `}` のリテラル、`{type}{n}` のように区切りがない書式を許すか。
  - 案: `{type}` と `{n}` はちょうど 1 回ずつ、改行(`\r` `\n`)を含む書式はエラー、それ以外は許す

### mask・hash

- **Q3(「同じ値」の判定)** 大文字・小文字の違う `Taro@Example.com` と `taro@example.com`、`2001:DB8::1` と `2001:db8::1`、UUID の大文字・小文字や `{}` の有無を同じ値として扱うか。同じ値として 1 つのラベルにすると、restore で 1 バイトも違わずに戻すことができなくなる(往復テストと矛盾)。
  - 案: mask はバイト列が完全に同じものだけを同じ値とする。hash も同じ扱い(入力のバイト列をそのままハッシュ)
- **Q4(番号の対象)** 連番は種別名(IP は区別込み)ごとに数える、で良いか(仕様 4.3 は IP について明記。他の種別も同様と読んでいる)。
- **Q18(HMAC の入力)** 「別のマシンでも同じ出力」のために、HMAC に渡すバイト列を固定する必要がある。値のバイト列だけか、種別名を前に付けるか(種別をまたいで同じ値が同じハッシュになるかが変わる)。`local` のときはローカルパートのバイト列か。16 進数は小文字か。
  - 案: 値のバイト列だけ(`local` はローカルパートだけ)、小文字の 16 進数
- **Q20(鍵)** `LOGSCRUB_KEY` と `--key-file` の両方がある場合の優先。`--key-file` の末尾の改行を除くか。空の値は未設定とみなすか。
  - 案: `--key-file` を優先、末尾の改行(`\n` / `\r\n` 1 つ)は除く、空はエラー
- **Q21(`--hash-length`)** 許す範囲。
  - 案: 8〜64(64 は SHA-256 の 16 進数の全桁)、範囲外はエラー
- **Q19(`--stats` と `--fail-on-detect`)** 件数は出現回数か、値の種類数か。`--allow` で残した値・特殊アドレス・`--ip-scope` 外は数えるか。出力形式。
  - 案: 置換した出現回数のみ数える。形式は 1 行 1 種別の `logscrub: email=3` のような形で、0 件の種別は出さない

### 種別ごと

- **Q5(email の正規表現)** 「一般的な」の範囲。
  - 案: ローカルパート `[A-Za-z0-9._%+-]+`、ドメイン `([A-Za-z0-9-]+\.)+[A-Za-z]{2,}`、大文字・小文字を区別しない、前後に `[A-Za-z0-9._%+-]` / `[A-Za-z0-9-]` が続かないこと。日本語などの非 ASCII 文字は「英数字でない」扱い。引用符つきのローカルパートや国際化ドメインは対象外
- **Q6(IPv6 のゾーン)** `fe80::1%eth0` の置換範囲に `%eth0` を含めるか。
  - 案: 含める(`<ipv6_private_1>` に置換)
- **Q7(先頭 0 付きの IPv4)** `192.168.001.001` は `netip.ParseAddr` が受け付けないため、仕様どおりだと検出されない。ログによってはゼロ埋めされることがあり、7 章「見逃しを減らす側」と食い違う。
  - 案: 仕様どおり検出しない(README の限界に書く)
- **Q8(IPv4 埋め込みの範囲)** 「埋め込まれた IPv4 で区別を判定」の対象は `::ffff:a.b.c.d`(IPv4-mapped)だけか、`::a.b.c.d`(IPv4-compatible、非推奨)や `64:ff9b::/96`(NAT64)も含むか。また `::ffff:0.0.0.0` のように埋め込み先が特殊アドレスなら置換しないか。
  - 案: IPv4-mapped のみ埋め込みとして扱い、埋め込み先が特殊なら置換しない
- **Q9(UUID の置換範囲)** `{123e4567-...}` と `urn:uuid:123e4567-...` で、置換するのは括弧・接頭辞を含む全体か、UUID 部分だけか。
  - 案: UUID 部分だけ(`{<uuid_1>}`、`urn:uuid:<uuid_1>`)。そうすると、括弧の有無で同じ値として扱える(Q3 とも整合)
- **Q13(`Bearer` / `Basic` の値の範囲)** 値の範囲の定義がない。また、大文字・小文字(`bearer`)を区別するか、`Authorization:` の後ろに限るか(文章中の「Bearer token is ...」も拾うか)。
  - 案: 方式名(`Bearer` / `Basic`)は大文字・小文字を区別せず、前が英数字でなく、後ろに空白が 1 つ以上あること。`Authorization:` の後ろに限らない(見逃しを減らす側)。値は RFC 7235 の token68 の文字(`A-Z a-z 0-9 - . _ ~ + /`、末尾に `=` が続いてもよい)が続く範囲。`Basic` だけは、値を base64 として解読でき、結果に `:` を含む(`user:pass` の形)場合に限る。英文の「Basic setup complete」のような誤検出を防ぐため(仕様の文面より絞り込む提案)
  - **改訂(2026-10-11)**: キー名の値の位置に限る(精度重視。SPEC 4.1、決定事項 15)。文章中の `Bearer abc` は対象外
- **Q14(固定形式の境界)** AWS(16 文字ちょうど)、Google(35 文字ちょうど)などで、前後に英数字が続く場合に検出するか。仕様は `sk-` だけ「前が英数字でない」と明記。JWT の各部の文字種(base64url)と、署名部が空の JWT(`alg: none`)の扱いも未定義。
  - 案: 全形式で「前後が英数字でない」を条件にする。JWT は `eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]*`(署名部は空でも可)
- **Q15(キーと値の区切りの空白)** `password = abc`、`token:  abc`(空白 2 つ)、`"key" : "value"` のように区切りの前後に空白がある場合を拾うか。仕様の区切り一覧(`=`、`:`、`: `、JSON)に含まれない。
  - 案: 区切りの前後の空白(スペース・タブ)は任意個を許す
- **Q16(閉じクォートがない値)** `password="abc` のように閉じクォートがない場合の値の範囲。
  - 案: 行末まで(見逃しを減らす側)
- **Q17(JSON の文字列以外の値)** `"token": 12345` や `"password": null` は、クォートなしの規則で `"token": <secret_1>` となり、JSON として不正になる。これで良いか。
  - 案: 仕様どおり置換する(`null`・`true`・`false` も置換)
  - **改訂(2026-10-11)**: キー名が引用符で囲まれた形(JSON、辞書)では、文字列の値だけを置換し、数値・`true`・`false`・`null`・`{`・`[` は置換しない(JSON の文法を壊さないため。決定事項 15)

### restore・CLI

- **Q22(複数ファイルの連結)** `mask a.log b.log` で、`a.log` が末尾改行なしで終わる場合、`a.log` の最後の行と `b.log` の最初の行を 1 行として検出するか(バイト列としての連結)、ファイルごとに行を区切るか。
  - 案: ファイルごとに行を区切る(値がファイルをまたがない)。出力のバイト列は各ファイルの出力をそのままつないだもの(間に改行を足さない)
- **Q23(戻せなかったラベルの数え方)** 同じラベルが回答に 2 回出た場合に 1 件と数えるか。一覧の並び順。「ラベル」と見なす範囲(既知の種別名でないもの、`<email_0>`、`<email_01>` は対象か)。
  - 案: 種類数で数え、回答に現れた順に並べる。ラベルとみなすのは、現在の書式で既知の種別名 + 1 以上の整数(先頭 0 なし)のものだけ
- **Q24(restore の入力)** 回答(ANSWER)全体をメモリに読んでよいか(DEVELOPMENT.md 3.3 節の最適化に使う)。ANSWER_FILE に `-` を指定した場合は stdin とみなすか。`--source` に同じ `-` を 2 回指定した場合はエラーか。
  - 案: すべて「はい」
- **Q25(hash 専用オプションと mask モード)** Q10 の案と合わせて、mask モードでの `--hash-length` `--email-hash` `--key-file` をエラーにしてよいか(無視する案もある)。
- **Q26(`--output` と入力が同じファイル)** `logscrub mask app.log -o app.log` は入力を消してしまう。
  - 案: 同じファイル(`os.SameFile`)ならエラー
- **Q27(`logscrub types` の出力形式)** 形式の指定がない。`ipv4` / `ipv6` を種別として出すか、`ipv4_global` などの区別まで出すか。
  - 案: 1 行 1 種別で `種別 ID  既定で有効かどうか  説明`。区別は説明の中で示す。`--verbose` で secret の形式一覧を追加
- **Q28(エラーと終了コード 2 の優先)** `--fail-on-detect` で検出ありの状態で、途中で書き込みエラーなどが起きた場合。
  - 案: エラー(1)を優先

### 性能・その他

- **Q29(50MB/s の測定条件)** どんなログで、どんな環境で測るか。
  - 案: 合成ログ(1 行 200 バイト前後、約 30% の行に何らかの検出対象、1MB の JSON 行を少し混ぜる)、既定の種別、mask モード、手元の WSL2 上の Docker コンテナ(`golang:1.27.2`)内で `cat file | logscrub mask > /dev/null` の実時間から算出。README の記録には CPU とコンテナ内での測定であることを併記する
- **Q30(モジュールパス)** `github.com/kiaamaaio/logscrub` で良いか。
- **Q31(置換済みの形として残した値の通知)** 利用者からの提案。置換済みのラベルや hash 出力形と同じ形の文字列を、置換せずに残した場合に stderr で知らせる。仕様にない出力の追加になる。
  - 案: 処理の最後に、1 件以上あれば 1 行だけ出す。件数と行番号(最初の 5 件まで)のみを出し、値は出さない(仕様 7 章)。例: `logscrub: 2 strings were left unchanged because they look already replaced (lines 12, 40). Check them before sharing.`
  - mask・hash・restore の `--source` で共通。restore では仕様 5.3 の限界(元の入力にラベルと同じ形の文字列がある)の検知にもなる
  - 終了コードは変えず、`--fail-on-detect` の件数にも含めない。抑止するオプションは設けない
  - 置換済みの出力をもう一度流すと、毎回この行が出る(元の値か前回の出力かを区別できないため)
