## 1. 範囲

v1.2.0 では、v1.1 の計画で後回しにした「着手順 5」(公開され得るサービスのホスト名)を対応する(仕様 決定事項 18、19)。

| 対象 | 種別 | 既定 | 仕様 |
|---|---|---|---|
| AWS のサービスのホスト名の、利用者ごとの部分(20 の形) | `aws_host`(新規) | 無効 | 4.5 |
| EC2 のパブリックホスト名の IPv6・デュアルスタック形式(`….<リージョン>.ip.aws`) | `aws_host` | 無効 | 4.3、4.5 |
| S3 Control のホストのアカウント ID(`<12 桁>.s3-control.…`) | `aws_account` | 無効 | 4.4 |
| URL のパスワード(`<スキーム>://<ユーザー>:<パスワード>@<ホスト>`)と、その形のときのメールアドレスの除外 | `secret`・`email` | 有効 | 4.1 |

2・3 行目は、v1.1 の Q38 で「v1.2 で検討する」とした候補のうち、形が決まっていて確実に判定できるもの。4 行目は、計画の作成時に見つかった問題への対応(Q48)。

範囲外:

- VPC の中からしかアクセスできないサービス(ElastiCache、DocumentDB、Neptune、VPC エンドポイント)→ Q49
- デュアルスタックのドメイン `api.aws` の形(AWS 自体の API のエンドポイントと区別できない。仕様 4.5「対象外」)
- アカウントのリージョン別の名前空間のバケット名の中のアカウント ID(v1.1 のまま、README の限界として扱う)

URL のパスワード(Q48)は既定で有効の種別(`secret`・`email`)の変更なので、**既定の動作が変わる**(`postgres://app:s3cret@db.example.com/` が `postgres://app:<email_1>/` から `postgres://app:<secret_1>@db.example.com/` になる、など)。
v1.1 の署名と同じく、隠せていなかった値を隠す方向の変更なので、マイナー版(v1.2.0)として扱う。README の変更点に明記する。

## 2. 設計の方針

### 2.1 種別の追加

- `detect.Kind` に `KindAWSHost` を加え、種別の表(`detect.Types`)に `aws_host`(既定は無効、クラウドは `aws`)を加える。まとまり `aws`・`cloud` は表から作られるので、定義を書き換えずに含まれる(v1.1 段階 1 の設計)
- `label.Types` に `aws_host` を加え、`NumTypes` を 10 にする。並び(連番・`--stats`・`logscrub types`)と、範囲の長さが同じときの優先順位は、`aws_s3_bucket` のあと
- `KindSet` は v1.1 で `uint32` に広げてあるので、変更は不要

### 2.2 `aws_host` の検出器

- `internal/detect/aws.go` に `awsHostFinder` を加える。仕様 4.5 の表を、**「末尾の形」の表(データ)**として持つ。サービスの追加は、表に行を足すだけで済むようにする
  - 末尾の形は、「決まった語の並び」と「リージョン」「ドメイン」の部品の組み合わせ。v1.1 の `awsDomains`・リージョンの文字・`isHostEnd`(Q41)をそのまま使う
  - 表の行は、「利用者ごとの部分として扱わない名前」(IoT の `data-ats`。Q57)を任意で持てる。持たない行が大半
  - 複数の形が当てはまる場合は長いほうを採る(仕様 4.5)。表の並びではなく、照合の結果で決める
- 利用者ごとの部分は、末尾の形の直前から手前へ、ホスト名に使える文字を遡って求める(v1.1 の S3 のバーチャルホスト形式と同じ考え方)。遡った長さの合計が行の長さ以内に収まるようにする(2 乗の時間にしない。v1.0 のレビューで直した問題と同じ)
- 前処理(DEVELOPMENT.md 3.4 節): 文中に少ない 1 バイトで手がかりを探し、前後を照合する(v1.1 の段階 6 のあとの改善と同じ方針)
  - 例: `amazonaws.` / `amazoncognito.` は `z`、`on.aws` / `ip.aws` は `.aws` の `w`、`cloudfront.net` などの独自ドメインは、それぞれ文中に少ない文字を選ぶ。どの文字を手がかりにするかは、実測で決める
- 正規表現の参照実装(全位置・末尾の形とドメインを 1 つずつ試す)との乱数テストで、結果が一致することを確認する

### 2.3 `aws_account` への追加(S3 Control)

- v1.1 の ECR の検出(`<12 桁>.dkr.ecr.…`)と同じ形なので、ECR のマーカーの表に `.s3-control.`・`.s3-control.dualstack.`・`.s3-control-fips.`・`.s3-control-fips.dualstack.` を加える形にする

### 2.4 URL のパスワード(Q48)

- `secret.go` の固定形式の 1 つとして加える。手がかりは `://` の `bytes.Index`(v1.1 の `s3://` と同じ)の予定だったが、実装では `@` の `bytes.IndexByte` に変えた(段階 5 の進捗参照)
- 「この形のときは `@` の前後をメールアドレスとして検出しない」は、メールアドレスの検出器(`email.go`)の側で、候補の `@` が URL のユーザー情報の `@` なら候補を出さない形にする。重なりの解決(DEVELOPMENT.md 3.1)の規則は変えない(長いほうが勝つ規則に例外を入れると、規則が分かりにくくなるため)
  - `secret` が無効(`--types email` など)の場合も、この形の `@` はメールアドレスとして扱わない(種別の有効・無効で、メールアドレスの判定が変わらないようにするため。Q54)
- 正規表現の参照実装 `refSecrets` と、メールアドレスの参照実装に、それぞれ加える

### 2.5 重なりと冪等性

- `aws_host` と他の種別は、仕様 4.5「対象外」で形が分かれているので、同じ範囲で競合しない。テストで次を固定する
  - EC2(`ec2-…compute.amazonaws.com`)・S3(`….s3.….amazonaws.com`)・ECR・S3 Control・SQS のホスト名は、`aws_host` にならない
  - `admin@<RDS のホスト名>` はメールアドレスになる(仕様 4.5「範囲が重なった場合」)
- hash の出力(`aws_host_<hex>.<リージョン>.rds.amazonaws.com`)が再検出されないこと、ラベル(`<aws_host_1>.…`)が再検出されないことをテストで固定する
- 既存のファズテスト(mask・hash の冪等性、restore の往復)の `--types default,aws` の種に、表の各サービスのホスト名を加える

## 3. 実装の段階

各段階は「その段階のテストがすべて通り、`go vet` も通る」状態で止められる。段階の終わりにコミットする。

### 段階 1: ホスト名の形の確認(Web)

前提となる確認: Q47

- 仕様 4.5 の表の「末尾の形」を、各サービスの AWS の公式ドキュメント(と、AWS SDK のエンドポイントの定義)で確認する
- 差があった場合や、確認できなかった形は、Q50 以降に書き足して止まる(仕様を推測で直さない)
- コードは変えない。確認の結果を Q47 の下に記録し、仕様の表に出典の日付を書いてコミットする

### 段階 2: 種別 `aws_host` の枠組み

- 2.1 節の変更。`logscrub types` の出力、`mask --help` の `--types` の説明、`--stats` の並び

- テスト: `ParseTypes`(`aws`・`cloud` に `aws_host` が含まれること)、`types` の出力、`--stats` の並び

### 段階 3: `aws_host` の検出器

前提となる確認: Q47、Q49〜Q53

- テスト: 表の各形(リージョン・ドメインの組み合わせ、大文字の ID)、長いほうの形を採ること、API のエンドポイント・表にない形・大文字の決まった部分・末尾の後ろの文字の除外、他の種別のホスト名との分担、利用者ごとの部分の境界(前の文字、`.` の連続、先頭・末尾の `-`)

### 段階 4: `aws_account` に S3 Control を追加

### 段階 5: URL のパスワード(Q48)

前提となる確認: なし(Q54 は確定済み)

- DEVELOPMENT.md: 2 章(種別の一覧)と 3.4 節(前処理の手がかりの一覧)を更新する

### 性能の改善(段階 7〜10)の調査

段階 6 までの完了後(2026-10-18)、AWS の処理を加えた状態の性能を調べた。

- 現状: 目標(50MB/s)は大きく上回っている(実バイナリ 既定 約 184MB/s、`--types default,aws` 約 138MB/s)。以下は必須ではなく、改善の余地
- `BenchmarkEngineMaskAWS`(`default,aws`、8MB、1 回 約 58ms)の CPU プロファイル:
  - AWS の 3 つの検出器で約 22%(`aws_host` 約 9%、`aws_s3_bucket` 約 8%、`aws_account` 約 5%)
  - `bytes.Index` が約 27%。呼び出し元は、`secret` の固定形式(`fixedLiterals`)が約 76%、`aws_s3_bucket` の `://`・`:s3:::` が約 20%
  - 原因は DEVELOPMENT.md 3.4 節の注意と同じ。先頭の文字が文中に多い(`sk` の `s` 約 5%、`rk` の `r`、`://` の `:` 約 2%)と、`bytes.Index` が遅い汎用の経路に切り替わる
- 代わりの実装を一時的なテストで試した(合成ログの全行と、乱数の 20 万行で、今の実装と結果が一致することを確認済み)。8MB あたりの時間:

| 対象 | 今 | 試した方法 | 試した結果 |
|---|---|---|---|
| `secret` の固定形式(既定の合成ログ) | 約 14.0ms(`BenchmarkFind` 約 37.6ms の約 37%) | 接頭辞ごとに、文中に少ない 1 バイトを `bytes.IndexByte` で探して前後を照合 | 約 8.0ms |
| `secret` の固定形式(AWS の合成ログ) | 約 13.3ms | 同上 | 約 7.5ms |
| `aws_s3_bucket` 全体 | 約 3.5ms | `://` と `:s3:::` を、`:` の `bytes.IndexByte` の 1 回の走査にまとめる | 約 2.4ms |
| `aws_host` | 約 4.7ms | 終端を `bytes.HasPrefix` で照合する前に、終端の先頭の `.` と、手がかりの次の 1 バイトを比べる | 約 3.6ms |

- 3 つを合わせると、`BenchmarkEngineMaskAWS` で約 8ms(約 14%)、既定の `BenchmarkFind` で約 6ms(約 16%)減る見込み(検出器ごとの測定からの見積もり。段階 10 で実測する)
- 検出の結果は変わらない(仕様の変更なし)。速さだけの変更
- 見送ったもの:
  - `.amazonaws.` の走査(`z` の `bytes.IndexByte`)を、`aws_account`・`aws_s3_bucket`・`aws_host` で共有する。1 回 約 0.67ms × 3 回で、共有しても減るのは最大 約 1.3ms(約 2%)。検出器の間で行ごとの前処理を共有する仕組みが要り、DEVELOPMENT.md 2 章で採らなかった「行ごとのヒント」に近い構造になる。効果に比べて変更が大きい
  - `:` の走査を、`aws_account` の ARN と `aws_s3_bucket` で共有する。同じ理由
  - `aws_host` の手がかりの文字の選び直し。段階 3 で実測して決めてあり、今回の 2 バイトの比較で、手がかりの一致の多さによる損は小さくなる

### 段階 7: `secret` の固定形式の手がかり

前提となる確認: Q62

- `fixedLiterals` を、接頭辞と手がかりの位置の組にする。手がかりは、試したときと同じ次の文字から始め、実測で決める
  - `AKIA`・`ASIA`・`AIza` は `A`、`gh`・`github_pat_` は `g`、`xox` は `x`、`sk`・`rk` は `k`、`eyJ` は `J`
  - 手がかりが同じ接頭辞を 1 回の走査にまとめるか(`aws_host` の `hostGroup` と同じ考え方)は、実測で比べて決める
- 各接頭辞の「次の出現位置」を覚える今の仕組み(`next`)はそのまま使う。接頭辞を探す部分だけを差し替える
- テスト: 今の実装(`bytes.Index` 版)をテストの中に参照実装として残し、乱数テスト(接頭辞・その一部・英数字・区切りの部品をつないだ行)で結果が一致することを確かめる。手がかりの位置を 1 つずらすと失敗することも確かめる
- 性能: `BenchmarkSecretFinder`・`BenchmarkFind`

### 段階 8: `aws_s3_bucket` の `://` と `:s3:::`

- `awsS3BucketFinder` の `schemes` と `arn` を、`:` の `bytes.IndexByte` の 1 回の走査にまとめる。`:` ごとに、後ろが `//` なら `s3://` などの形、`:s3:::` で始まるなら ARN の形を調べる
- テスト: 今の `schemes`・`arn` をテストの中に参照実装として残し、乱数テストで一致を確かめる。既存の S3 のテスト(正規表現の参照実装との乱数テストを含む)が通ること
- 性能: `BenchmarkAWSS3BucketFinder`

### 段階 9: `aws_host` の終端の照合

- `awsHostFinder.find` で、終端を `bytes.HasPrefix` で照合する前に、終端の先頭(`.`)と、手がかりの次の 1 バイトを比べる。`.amazonaws.` の照合も、先頭の `.` を先に比べる
  - 手がかりが終端の最後の 1 バイトの場合(今の表にはない)や、行末の手前の場合に、比べる位置が行の外に出ないようにする
- テスト: 既存の正規表現の参照実装との乱数テスト(8 万回)が通ること。行末・行頭の近くの終端(`x.cloudfront.net` で終わる行、`l` だけの行など)を加える
- 性能: `BenchmarkAWSHostFinder`

### 段階 10: 測定と資料

- ベンチマーク(`BenchmarkFind`、`BenchmarkEngineMask`、`BenchmarkEngineMaskAWS`、検出器ごと)と、実バイナリ(段階 6 と同じ 6 通り)を測り、6 章のベンチマーク記録に書く
- ファズテスト(`FuzzMaskStable`・`FuzzHashStable`・`FuzzRestoreRoundTrip`)を各 90 秒実行する
- DEVELOPMENT.md 3.4 節(固定形式の secret と、S3 の手がかりの記述、実測)と、README の性能の表を更新する
