## 1. 範囲

v1.2.0 では、v1.1 の計画で後回しにした「着手順 5」(公開され得るサービスのホスト名)を対応する(仕様 決定事項 18、19)。

| 対象 | 種別 | 既定 | 仕様 |
|---|---|---|---|
| AWS のサービスのホスト名の、利用者ごとの部分(20 の形) | `aws_host`(新規) | 無効 | 4.5 |
| EC2 のパブリックホスト名の IPv6・デュアルスタック形式(`….<リージョン>.ip.aws`) | `aws_host` | 無効 | 4.3、4.5 |
| S3 Control のホストのアカウント ID(`<12 桁>.s3-control.…`) | `aws_account` | 無効 | 4.4 |
| URL のパスワード(`<スキーム>://<ユーザー>:<パスワード>@<ホスト>`)と、その形のときのメールアドレスの除外 | `secret`・`email` | 有効 | 4.1 |

2・3 行目は、v1.1 の Q38 で「v1.2 で検討する」とした候補のうち、形が決まっていて確実に判定できるもの。4 行目は、計画の作成時に見つかった問題への対応(Q48)。

範囲外:

- VPC の中からしかアクセスできないサービス(ElastiCache、DocumentDB、Neptune、VPC エンドポイント)→ Q49
- デュアルスタックのドメイン `api.aws` の形(AWS 自体の API のエンドポイントと区別できない。仕様 4.5「対象外」)
- アカウントのリージョン別の名前空間のバケット名の中のアカウント ID(v1.1 のまま、README の限界として扱う)

URL のパスワード(Q48)は既定で有効の種別(`secret`・`email`)の変更なので、**既定の動作が変わる**(`postgres://app:s3cret@db.example.com/` が `postgres://app:<email_1>/` から `postgres://app:<secret_1>@db.example.com/` になる、など)。
v1.1 の署名と同じく、隠せていなかった値を隠す方向の変更なので、マイナー版(v1.2.0)として扱う。README の変更点に明記する。

## 2. 設計の方針

### 2.1 種別の追加

- `detect.Kind` に `KindAWSHost` を加え、種別の表(`detect.Types`)に `aws_host`(既定は無効、クラウドは `aws`)を加える。まとまり `aws`・`cloud` は表から作られるので、定義を書き換えずに含まれる(v1.1 段階 1 の設計)
- `label.Types` に `aws_host` を加え、`NumTypes` を 10 にする。並び(連番・`--stats`・`logscrub types`)と、範囲の長さが同じときの優先順位は、`aws_s3_bucket` のあと
- `KindSet` は v1.1 で `uint32` に広げてあるので、変更は不要

### 2.2 `aws_host` の検出器

- `internal/detect/aws.go` に `awsHostFinder` を加える。仕様 4.5 の表を、**「末尾の形」の表(データ)**として持つ。サービスの追加は、表に行を足すだけで済むようにする
  - 末尾の形は、「決まった語の並び」と「リージョン」「ドメイン」の部品の組み合わせ。v1.1 の `awsDomains`・リージョンの文字・`isHostEnd`(Q41)をそのまま使う
  - 複数の形が当てはまる場合は長いほうを採る(仕様 4.5)。表の並びではなく、照合の結果で決める
- 利用者ごとの部分は、末尾の形の直前から手前へ、ホスト名に使える文字を遡って求める(v1.1 の S3 のバーチャルホスト形式と同じ考え方)。遡った長さの合計が行の長さ以内に収まるようにする(2 乗の時間にしない。v1.0 のレビューで直した問題と同じ)
- 前処理(DEVELOPMENT.md 3.4 節): 文中に少ない 1 バイトで手がかりを探し、前後を照合する(v1.1 の段階 6 のあとの改善と同じ方針)
  - 例: `amazonaws.` / `amazoncognito.` は `z`、`on.aws` / `ip.aws` は `.aws` の `w`、`cloudfront.net` などの独自ドメインは、それぞれ文中に少ない文字を選ぶ。どの文字を手がかりにするかは、実測で決める
- 正規表現の参照実装(全位置・末尾の形とドメインを 1 つずつ試す)との乱数テストで、結果が一致することを確認する

### 2.3 `aws_account` への追加(S3 Control)

- v1.1 の ECR の検出(`<12 桁>.dkr.ecr.…`)と同じ形なので、ECR のマーカーの表に `.s3-control.`・`.s3-control.dualstack.`・`.s3-control-fips.`・`.s3-control-fips.dualstack.` を加える形にする

### 2.4 URL のパスワード(Q48)

- `secret.go` の固定形式の 1 つとして加える。手がかりは `://` の `bytes.Index`(v1.1 の `s3://` と同じ)
- 「この形のときは `@` の前後をメールアドレスとして検出しない」は、メールアドレスの検出器(`email.go`)の側で、候補の `@` が URL のユーザー情報の `@` なら候補を出さない形にする。重なりの解決(DEVELOPMENT.md 3.1)の規則は変えない(長いほうが勝つ規則に例外を入れると、規則が分かりにくくなるため)
  - `secret` が無効(`--types email` など)の場合も、この形の `@` はメールアドレスとして扱わない(種別の有効・無効で、メールアドレスの判定が変わらないようにするため)。この点は段階 5 の前に確認する(Q54)
- 正規表現の参照実装 `refSecrets` と、メールアドレスの参照実装に、それぞれ加える

### 2.5 重なりと冪等性

- `aws_host` と他の種別は、仕様 4.5「対象外」で形が分かれているので、同じ範囲で競合しない。テストで次を固定する
  - EC2(`ec2-…compute.amazonaws.com`)・S3(`….s3.….amazonaws.com`)・ECR・S3 Control・SQS のホスト名は、`aws_host` にならない
  - `admin@<RDS のホスト名>` はメールアドレスになる(仕様 4.5「範囲が重なった場合」)
- hash の出力(`aws_host_<hex>.<リージョン>.rds.amazonaws.com`)が再検出されないこと、ラベル(`<aws_host_1>.…`)が再検出されないことをテストで固定する
- 既存のファズテスト(mask・hash の冪等性、restore の往復)の `--types default,aws` の種に、表の各サービスのホスト名を加える

前提となる確認: Q47、Q49〜Q53

## 5. 未確定事項

推測では埋めず、回答をもらってから該当する段階に入る。「案」は判断材料としての提案で、仕様書には案のとおりに書いてある。採用は回答後。
番号は v1.1.0 の計画(Q32〜Q46)から続ける。

**2026-10-17: Q47〜Q53 はすべて確定。** Q48 は「v1.2 に含める」(仕様 4.1、決定事項 20 に反映)。それ以外は案どおり。

- **Q47(ホスト名の形の確認)** 仕様 4.5 の表の 20 の形のうち、計画の作成時(2026-10-17)に公式ドキュメントで確認できたのは、ELB(NLB の `.elb.<リージョン>.` と、ALB・CLB の `.<リージョン>.elb.`)、EKS(`<ID>.<リージョン>.eks.amazonaws.com`。ID とリージョンの間に `gr7` のような短いラベルが入る例がある)、EC2 の `.ip.aws` だけ。MSK は `-public` の付いたブローカー名があることまで確認した。Amazon MQ・Redshift Serverless は、公式の形を確認できていない
  - 案: 段階 1 で、残りの形を公式ドキュメント(または AWS SDK のエンドポイントの定義)で確認する。確認できなかった形は、表から外すか、確認できた範囲に絞る(精度重視の方針。決定事項 16)
  - なお、「末尾の形より前をまとめて置換する」規則なので、確認が必要なのは**末尾の形だけ**で、利用者ごとの部分の細かい形(EKS の `gr7` のようなラベルなど)は確認しなくてよい
- **Q48(DB の接続 URL のパスワード)** 計画の作成時に、v1.1.0 で次の動作を確認した。
  - `postgres://app:s3cret@mydb.cluster-….rds.amazonaws.com:5432/app` → `postgres://app:<email_1>:5432/app`
  - 既存のメールアドレスの規則で、`s3cret@<ホスト名>` 全体がメールアドレスとして置換される。パスワードは結果として隠れているが、種別が誤っており、`aws_host` を有効にしても RDS のホスト名だという情報が消える。また、ホスト名が IP アドレスの場合(`https://user:pass@10.0.0.1/`。v1.0 の受け入れ基準)は、**パスワードがそのまま残る**
  - 案: v1.2 の範囲に入れる。`secret` に「URL のユーザー情報のパスワード」(`<スキーム>://<ユーザー>:<パスワード>@`)を加え、その形のときは `@` の前後をメールアドレスとして扱わない。結果は `postgres://app:<secret_1>@<aws_host_1>.ap-northeast-1.rds.amazonaws.com:5432/app` になる。ただし、`secret`・`email` は既定で有効の種別なので、**既定の動作が変わる**(v1.1 の署名と同じく、隠せていなかった値を隠す方向の変更)
  - 別案: v1.2 では扱わず、別の版にする(v1.2 は「着手順 5 のみ」という当初の範囲を守る)。その場合、README の限界に書く
  - **回答(2026-10-17)**: v1.2 に含める
- **Q49(VPC の中からしかアクセスできないサービス)** ElastiCache(`.cache.amazonaws.com`)、DocumentDB、Neptune、VPC エンドポイントのホスト名も、組織を特定できる値で、形も決まっている。
  - 案: v1.2 では対象外とする(当初の範囲「設定によって AWS の外からアクセスできるもの」を守る)。必要になった時点で、表に行を足すだけで追加できる
- **Q50(`api.aws` の形)** EKS の IPv6 のクラスタは `<ID>.<リージョン>.api.aws` という形のエンドポイントを使う。一方 `api.aws` は、AWS 自体の API のデュアルスタックのエンドポイント(`sqs.us-east-1.api.aws` など)にも使われ、末尾の形だけでは区別できない。
  - 案: 対象外とする(仕様 4.5「対象外」)。README の限界に書く
- **Q51(接頭辞の扱い)** `dualstack.`(ELB)、`internal-`(内部向けの ELB)、アベイラビリティゾーンの接頭辞(NLB の `us-east-2a.`)を、利用者ごとの部分に含めるか、外して残すか。
  - 案: 含める(仕様 4.5)。外すと、サービスごとに接頭辞の表が必要になり、規則が複雑になる。同じロードバランサが接頭辞の有無で別のラベルになる点は、README の限界に書く
- **Q52(利用者ごとの部分の英大文字)** v1.1 の Q42 では「決まった部分は小文字だけ」とした。利用者ごとの部分は、EKS の ID のように AWS が大文字で付ける値がある。
  - 案: 利用者ごとの部分は英大文字を許す(仕様 4.5)。決まった部分(末尾の形)は、Q42 のとおり小文字だけ
- **Q53(S3 Control と EC2 の `.ip.aws` を v1.2 に入れること)** v1.1 の Q38 で「v1.2 で検討する」とした 3 つの候補のうち、S3 Control のホスト(`aws_account`)と EC2 の `.ip.aws`(`aws_host`)を入れ、アカウントのリージョン別の名前空間のバケット名の中のアカウント ID は入れない。
  - 案: 上のとおり(仕様 4.3〜4.5)。バケット名の中のアカウント ID は、バケット名の文脈の中だけで判定する必要があり、`aws_s3_bucket` を有効にすれば名前ごと隠れるため、v1.1 のまま README の限界として扱う

- **Q54(`secret` が無効なときのメールアドレスの除外)** `--types email` のように `secret` を無効にした場合も、`<スキーム>://<ユーザー>:<パスワード>@<ホスト>` の `@` をメールアドレスとして扱わないか。
  - 案: 扱わない(2.4 節)。メールアドレスの判定が、他の種別の有効・無効で変わると分かりにくいため。その場合、`--types email` ではパスワードが残る(`secret` を無効にした利用者の選択どおり)
  - 段階 5 の前に確認する(仕様にはまだ書いていない)
