# v1.5.0 の対象(#13、#14、#16、#19)の事前調査

- 目的: 4 件の issue の「決めること」に答えるために、今の動作と、実装の制約を確かめる
- 確認日: 2026-11-01
- 対象の版やコミット: `develop` の 6972f69(v1.4.0 の後)
- 範囲外: 実装の試作、速度の測定

## 結論

- 4 件とも、標準ライブラリだけで実装できる見込み。`--review` の色に端末の判定を使わなければ、外部のライブラリは候補にも上がらない
- #14 は、行ごとに別のラベルにすれば、`Masker` と `restore` を変えずに 1 バイトも違わずに戻せる。ブロックで 1 つの値にすると、行をまたぐ値が要り、1 行の中で閉じている今の書き換えの前提が崩れる
- #14 の状態は、読み取りの段(`readBlocks`)に置ける。ブロックは完全な行だけを含み、入力ごとに読み手が分かれるので、印が境目で切れず、状態を入力ごとに戻せる(Q98 の見込みの確認。速度は未測定)
- #13 を既定で有効にしても、既存のゴールデンは変わらない。`PWD=/home/user` の 3 つのテストだけが影響を受ける
- #19 は、`Engine.Run` をファイルごとに呼べば実現できる。`Masker` と `Stats` を引き継ぐので、連番は `mask a b` と同じになる見込み

## 確かめた事実

実行したバイナリは `./scripts/go build -o bin/logscrub ./cmd/logscrub` で作った。入力は架空の値。

| 確認したこと | 確かめた方法 | 結果 |
|---|---|---|
| 複数行の PEM の本文 | `logscrub mask` に架空の base64 の行で流す | 本文がすべてそのまま残る |

| `private_key: "-----BEGIN PRIVATE KEY-----` | 同上 | `private_key: "<secret_N>`。閉じ引用符がなく、行末までが値 |

## 推測・未確認

- PEM の印を `bytes.Index` で探す費用は、読み取りの段の律速にならないと見込むが、測っていない
- `user_path` の検出を既定で足したときの、既定の mask の速度の低下は、測っていない
- PEM の本文の形(RFC 7468、RFC 1421 の `Proc-Type`・`DEK-Info`)、1 行の長さが 64 または 70 文字であることは、一般的な知識によるもので、今回は原文を確かめていない
- 除外の名前の候補(`ubuntu`、`ec2-user`、`Public` など)は、クラウドのイメージや OS の既定の名前という知識によるもので、今回は一覧を確かめていない
- `NO_COLOR` の慣習は、一般的な知識によるもので、今回は原文を確かめていない
- Windows の古いコンソールで、ANSI の色の指定が表示されるかは、確かめていない。手元の環境では自動で確かめられない

## 判断に影響すること

- `user` を除外の名前に入れれば、`PWD=/home/user` の既存の期待値を変えずに、既定で有効にできる
- 「`-----BEGIN … PRIVATE KEY-----` の文字列がログの文章やコードに現れるだけ」の場合がある。END がないときに入力の終わりまで伏せる規則だと、その後ろがすべて消える
- 行の先頭に日時などが付く形では、本文の形を厳しくすると、最初の本文の行でブロックが終わり、鍵が残る
- `--review` の出力は、ログの中の制御文字をそのまま流すと、端末の表示で隠せてしまう。確認の用途なので、見える形に変える必要がある
